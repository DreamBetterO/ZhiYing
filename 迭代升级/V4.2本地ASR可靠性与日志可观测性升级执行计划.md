# V4.2 本地 ASR 可靠性与日志可观测性升级执行计划

> 状态：已实施但未通过最终实机验收；2026-08-16 复核确认模型权重完整，Qwen3-ASR 隔离 runtime 和便携装配仍有缺口。后续以 [`V4.2本地ASR实机复核与收尾修复清单.md`](V4.2本地ASR实机复核与收尾修复清单.md) 为唯一收尾入口。  
> 版本类型：小版本。保留现有 15 步顺序、Artifact 合同、Document v2、桌面边界和云端授权边界；拟发布产品版本 `0.4.2`。  
> 取证日期：2026-08-15（Asia/Shanghai）。
> 批准日期：2026-08-15（Asia/Shanghai）。

## 0. 可行性审计结论

综合把握度：**94%**，可以交由后续 Agent 按阶段实施。

- **合理性**：升级顺序沿“日志事实源 → 进程边界与错误分类 → 模型链降级 → Qwen 真实进度与性能 → UI 单一投影”推进，先恢复可诊断性再优化性能，能够避免继续依赖假进度和错误归因。
- **可行性**：faster-whisper 的序列化失败、异常误分类和 `engine_chain` 断链已有代码与日志闭环证据；Qwen 官方 Transformers 后端明确支持本地路径、批量输入和受限 batch，现有 60 秒逻辑块可继续作为时间戳边界。
- **架构影响可控**：不改变 15 步顺序、Artifact/Document v2、JSON → Markdown → Word → PDF、云端 opt-in 或桌面产品边界；新增内容主要位于 ASR adapter/runner、事件合同、Application 状态投影和 View。
- **剩余不确定性有封口**：不同机器的最优 batch 和实际 RTF 不能在编码前承诺，因此用 capability probe、真实热态测量、画像失效、OOM 有界回退和速度熔断决定是否继续；达不到门禁就透明降级到 faster-whisper。
- **唯一前置授权**：当前隔离 runtime 缺少官方 `qwen-asr` 包。P0–P2 可先执行；进入 P3 的真实官方后端集成前，必须另获“更新隔离 ASR runtime 依赖”授权。真实模型烟测、模型下载和长视频重跑仍分别受原授权边界约束。

把握度未计为 100% 的原因仅是官方 runtime 在当前 Windows 隔离环境中的依赖组合和目标 GPU 上的实测速率尚未验证；这两项不影响修复链路的设计成立，也不会被静默当作成功。

## 1. 本次升级要解决什么

V4.2 不把“日志多”当作“日志完整”，也不先凭感觉调整模型参数。执行顺序固定为：

1. 先建立可信、低噪声、可定位到 ASR 尝试的日志合同；
2. 再修复已经由现有证据确认的执行错误和降级断链；
3. 再用真实块进度测量 Qwen3-ASR，把“加载慢、CPU 执行、单块慢、长视频块数多”分开；
4. 最后把同一结构化事实投影成两行独立 UI 状态，并统一业务错误文案和复选框视觉。

本次不改变知识整理、VLM、云端精炼、聚合、拖动排序、单实例互斥、缓存清理、产物可见性、Word/PDF 回看等既有功能。

## 2. 已取得的事实证据

### 2.1 faster-whisper：真正故障点在子进程启动前

证据 Workspace：`workspace/高数-2d5be9b875cb-faster-whisper`；run：`3e4dc329aa71432dbdae490982ea4e95`。

- 视频源探测、音频提取和 600 张候选画面提取均成功；`transcript.decode` 在 0.25 秒内失败。
- 失败正文是 `TypeError: cannot pickle 'mappingproxy' object`，不是 CUDA DLL、显存不足或模型推理错误。
- `ProcessingOptions` 会递归把嵌套配置冻结为 `MappingProxyType`；`SpeechAdapter` 和 `_transcribe_once` 只做浅层 `dict`/筛选，`terminology_replacements` 等嵌套对象仍是 `mappingproxy`。
- Windows `multiprocessing spawn` 在 `process.start()` 序列化参数时失败，worker 尚未开始加载 faster-whisper。
- `decode_audio` 把 CUDA 路径上的所有异常一律归类为 `asr_cuda_fallback`，所以 UI/日志错误地显示“GPU 识别不可用”；CPU 重试仍携带同一个不可序列化对象，立即再次失败。
- 桌面请求传入的是 `engine_chain`，`TranscriptDecodeStep` 却只读取 `_engine_chain`。日志虽然记录了 `[faster-whisper, qwen3-asr-0.6b]`，实际只执行首个模型，未按用户选择降级到 Qwen3-ASR。
- `transcript.normalize` 至 `render.bundle` 的 skipped 全是 `transcript.decode` 失败后的依赖传播，不是十余个独立错误。

结论：必须同时修复“进程参数边界”“异常分类”“模型链键名”三处；只安装 CUDA 或只改错误文案不会修通链路。

### 2.2 Qwen3-ASR：当前日志无法证明模型本身为何慢

证据 Workspace：`workspace/高数-2d5be9b875cb-qwen3-asr-0.6b`；run：`c86ad57abbc54d06aedf2f5d36dabee7`。

- 视频时长 `10083.012987` 秒，约 2 小时 48 分；固定 60 秒切块意味着约 169 个块，runner 当前逐块串行调用，`max_inference_batch_size=1`。
- run 在 `transcript.decode` 运行中被外部中断；JSONL 最后一条事件的运行耗时约 75.7 秒，没有成功、失败或取消终态，也没有 transcript Artifact。
- runner 实际会输出 `[qwen-asr] 当前块/总块数`，父进程却只把 stdout/stderr 放进内存尾部队列，成功路径完全不解析、不记日志；因此看不到模型加载结束、首块开始、首块完成和真实块速率。
- 父进程每 250 ms 以 `elapsed / (duration * 0.35)` 生成“活动进度”。这不是已处理音频量；在该视频上它预设约 58.8 分钟才到 95%，会让 UI 长时间停留在约 20%。
- 该 run 的 JSONL 有 376 条，其中 `stage_progress` 174 条、`task_progress` 181 条；绝大部分是同一假进度的高频重复，不含真实块证据。
- summary 只在 Step 生命周期或警告/错误时刷新，仍停在 33 条事件；JSONL 已有 376 条。外部中断后 summary 仍永久显示 `running`。

结论：可以确认“长视频串行 169 块”和“进度/日志设计失真”，但现有证据不足以在 GPU、CPU、模型加载或单块推理之间作进一步归因。V4.2 必须先接通真实进度协议，再决定是否需要运行时复用、块长调整或设备修复。

### 2.3 UI 四行重复不是 Text 控件单点问题

一次 ASR progress 回调目前会走四条展示路径：

1. `stage_progress_sink -> journal.publish -> handle.publish`；
2. `stage_progress_sink -> progress callback -> handle.publish`；
3. `progress_sink -> journal.publish -> handle.publish`；
4. `progress_sink -> task_progress callback -> handle.publish`。

Controller 对没有顶层 message 的 task progress 还会复用上一条 message；View 再把最近四条文本滚动保存，所以最终表现为四行成对重复。仅把 `[-4:]` 改成 `[-2:]` 仍会得到两条重复消息，不能满足“两行独立”。

### 2.4 完整日志与诊断工具仍有断点

- ASR runtime 事件缺少稳定 `type` 和所属业务 `step_id`，被记录为 `unknown` / `runtime`，难以按 `transcript.decode` 聚合。
- 人类可读 `.log` 只展开 status、cache reason、error code、duration，丢失模型、设备、attempt、块号、子进程退出码和经过脱敏的 stderr 尾部。
- `scripts/diagnose_workspace.py` 反向选择最后一个 `status=failed` 事件时，被最末尾的 `run_failed` 覆盖，当前输出错误地成为 `last_failed_step=run`、空 error code、空 owner、建议从 run 重跑；正确责任点应是 `transcript.decode / TRANSCRIPT_DECODE_*`。
- 被复制并加后缀的取证 Workspace 内，summary/manifest 仍保存原 Workspace 绝对路径。诊断时应以用户传入的 Workspace 为定位根，并把“记录时路径”和“当前解析路径”区分显示。

### 2.5 “记住 API Key”显示为叉号的原因

View 全局强制使用 `clam` ttk 主题，当前 `ttk.Checkbutton` 完全依赖该主题的 indicator 图形；在当前 Windows 环境中选中态呈现为叉号。布尔变量和保存逻辑本身正常，问题是视觉控件未定义跨主题一致的选中图形。

### 2.6 Qwen3-ASR 二次取证：当前没有使用官方高吞吐路径

- 当前机器是 RTX 4060 Laptop GPU，8GB 显存。runner 把 `models/qwen3-asr-runtime` 插到 `sys.path` 首位后，实际使用其中的 PyTorch `2.7.1+cu128`，该 runtime 能识别 CUDA 和 RTX 4060；不能简单归因为“机器没有 GPU”。
- 配置所指 Anaconda 环境自身的 PyTorch `2.4.1+cu121` 导入时存在 `cublas64_12.dll` 访问拒绝，但 runner 当前会被 bundled runtime 覆盖。V4.2 仍需把“解释器、实际 torch 来源、CUDA 可用性”作为启动前检查，避免环境切换后行为漂移。
- bundled runtime 中不存在 `qwen_asr` 官方包，也没有 FlashAttention；`_load_official_backend()` 必然进入 `ModuleNotFoundError`，随后静默回落到 `_load_legacy_backend()`。
- legacy 分支使用 `AutoModelForMultimodalLM.generate()`，对每个 60 秒块单独调用一次；runner 固定 `max_inference_batch_size=1`，没有调用官方 `Qwen3ASRModel` 的长音频拆块和 batch inference 能力。
- 官方说明 Qwen3-ASR Transformers 后端支持批量输入，`max_inference_batch_size` 默认可大于 1；官方最快方案是 vLLM，但 vLLM 官方不原生支持 Windows。本项目又禁止本地 HTTP 服务和端口，因此 V4.2 不把 vLLM server、WSL、Docker 或社区 Windows fork 引入默认桌面产品。

结论：Qwen3-ASR 可以合理变快，但第一优先级不是盲目调大 chunk，而是换掉当前逐块 legacy 调用，接入可审计的官方 Transformers 推理封装，并在本机 8GB 显存范围内进行自适应批处理和模型复用。

## 3. V4.2 目标合同

### 3.1 ASR Attempt 合同

每个语音模型尝试都有稳定 `attempt_id`，至少记录以下语义事件：

- `asr_attempt_started`：step、engine、model identity、requested device、chunk seconds、audio duration、estimated chunk count、runtime identity；
- `asr_model_load_started` / `asr_model_load_completed`：加载耗时和最终设备/compute type；
- `asr_chunk_completed`：真实块号、总块数、音频起止、块耗时、累计实时率；
- `asr_attempt_degraded`：明确失败分类、下一模型及降级原因；
- `asr_attempt_succeeded` / `asr_attempt_failed` / `asr_attempt_cancelled`：终态、总耗时、segment 数、退出码和脱敏诊断尾部。

所有跨进程参数先转换为普通 dict/list/string/number/bool/null，并在启动前执行可序列化校验。任何 `process.start()` 前失败归类为“worker 启动/参数合同错误”，不得误报 CUDA。

### 3.2 本地语音模型下拉框与降级合同

- Desktop 不再让用户编辑逗号分隔的“语音模型链”，改为单个下拉框，只有两个稳定选项：
  - `faster-whisper（高速）`，内部值 `faster-whisper`，默认项；
  - `Qwen3-ASR（方言）`，内部值 `qwen3-asr-0.6b`。
- 下拉框表达“首选模型”。为了保持失败降级能力，Application 会把首选模型放在第一位、另一个本地模型放在第二位形成内部 `engine_chain`；设置区明确提示“首选失败时会自动尝试另一模型，并标记为降级”。不得静默改变最终 engine。
- 只保留公开配置键 `engine_chain`，从 Desktop Request 到 ProcessingOptions 再到 `TranscriptDecodeStep` 一名到底；不再以 `_engine_chain` 作为隐式旁路。CLI/旧配置显式提供的合法顺序继续兼容。
- 首选失败、后备成功时，`transcript.decode` 终态为 `degraded`，后续 14 步正常继续；diagnostics 和 UI 保存/显示首选、实际 engine 与降级原因。
- 两个本地模型都失败时才令 Step `failed`；后续 skipped 保留 `blocked_by`，UI 只呈现一个首要业务失败。
- 旧 `desktop.speech_models` 首次读取时取第一项作为下拉首选，保存后写稳定单值配置；Artifact 格式和有效缓存不变，不因 UI 或日志升级强制重跑。

### 3.3 Qwen3-ASR 真实进度合同

- runner 使用机器可解析的 JSON Lines 输出控制事件；stderr 只承载诊断文本并统一脱敏、限长。
- 模型加载期间显示“不确定进度/正在加载”，不得把墙钟时间伪装成已处理音频。
- 每完成一个真实音频块才推进 `completed_audio_seconds`；ETA 至少有两个完成块后才计算，采用实际块耗时平滑估计。
- 日志按“阶段变化、每块完成、异常、终态”写入，不再每 250 ms 生成两条无新增信息的记录。
- 默认使用本地、离线的官方 `qwen-asr` Transformers 后端；启动时必须记录包版本、torch 来源、CUDA、GPU、dtype 和 attention backend，官方包缺失时不得静默冒充同一性能档位。
- 通过能力预检的 GPU 优先使用 CUDA，dtype、attention 和 batch 均由下节动态策略决定；保持 60 秒逻辑块以保留现有粗粒度时间戳，再将多个块组成动态小批次，不暴露复杂设置给用户。
- 同一桌面处理队列选择 Qwen 时复用一个模型 worker，避免每个视频重新加载；取消、应用退出或切换模型时必须结束 worker 并释放显存，不能变成本地服务或端口监听器。
- 不默认引入 vLLM、WSL、Docker、社区 Windows fork或本地 HTTP server；不把 FlashAttention 作为硬依赖。它们若将来需要，必须另立升级并重新评估桌面边界、安装和回滚。
- 性能优化设条件门：先得到 legacy baseline、device、load time、首批/p50 批次实时率。CPU 执行优先修设备识别；加载占主导启用队列内复用；推理占主导只对同一短样本做一次受控 batch A/B。未经证据不得直接扩大 chunk 或 token 上限。

### 3.4 动态设备、模型加载与批量调优合同

V4.2 不维护“4060 参数”“5070 参数”等显卡型号表。所有策略只依赖运行时能力和实测结果：

1. **精确 runtime 预检**：在 runner 实际使用的 Python/sys.path 中读取 torch、CUDA runtime、driver、可见 GPU、compute capability、当前空闲/总显存、BF16、SDPA backend；执行一个极小 CUDA 分配/算子以排除“能枚举 GPU 但 DLL/kernel 不可用”。
2. **动态设备选择**：只在可见设备中选择可用显存最多且通过算子预检的 GPU；没有合格 GPU、runtime 不支持新显卡架构或显存不足时，不进入数小时 CPU 推理，立即把 Qwen attempt 标为能力不足并降级到 faster-whisper。
3. **动态 dtype/attention**：GPU 支持 BF16 就用 BF16，否则尝试 FP16；优先使用 PyTorch SDPA，并记录请求配置、实际可用能力和运行库返回的有效实现；不按显卡名称猜测，也不强制依赖外部 FlashAttention 包。
4. **低峰值加载**：使用本地权重、`low_cpu_mem_usage` 和 inference/eval 模式；本地权重与运行库支持时优先采用 safetensors 的低复制/映射加载；不加载 forced aligner，不在运行时下载文件。加载前根据本地权重大小与实时空闲显存保留安全余量，加载后重新测量模型常驻显存。
5. **无重复在线校准**：没有有效 profile 时，第 1 个真实块用 batch=1；后续尚未处理的块按 `1 -> 2 -> 4 -> ...` 有界增长。每一步用真实完成时间和 peak VRAM 判断是否继续，音频块不为基准测试重复推理；收益不足或安全余量触底即停止增长。
6. **OOM 有界回退**：某批次 OOM 时仅对该未提交批次按 `N -> N/2 -> 1` 重试，清理临时张量并写日志；batch=1 仍失败则降级到 faster-whisper，禁止无穷试探。
7. **设备画像缓存**：只保存成功 profile，键包含 model digest、official backend/qwen-asr 版本、torch/CUDA、driver major、GPU UUID/compute capability/总显存。runtime、模型、驱动或设备变化自动失效；当次空闲显存低于历史条件时临时缩小 batch，不污染稳定画像。
8. **按队列复用模型**：Qwen worker 首次遇到真实 ASR cache miss 才加载；同一桌面队列后续 Qwen 视频复用，队列完成、取消、切换模型或应用退出即卸载。它是受 Controller 生命周期管理的子进程，不是常驻服务，也不开端口。
9. **速度熔断**：有效画像命中时可结合首个完成批次计算预测 RTF；没有画像时至少完成两个不含模型加载时间的真实批次，再以滚动热态 RTF 判断。若达不到最低放行线，停止继续消耗长视频时间，业务化说明后降级到 faster-whisper。这样较旧、低显存或 runtime 尚未支持的新 GPU 都不会表现为“进度很慢但一直跑”。

动态画像放在可清理的本地 runtime cache，不进入用户配置、不携带秘密、不影响 Workspace Artifact 指纹；UI 只显示“自动选择的设备、精度、批量和预计速度”，不给普通用户增加参数。

### 3.5 日志与终态合同

- JSONL 仍是完整事实源，sequence 单调；summary 是可重建索引，不可与 JSONL 长期失配。
- summary 在语义检查点限频刷新，运行终态时 `event_count` 必须等于 JSONL 有效事件数。
- 正常取消必须写 `run_cancelled`；进程崩溃/强退无法现场收尾时，下一次读取或运行要把旧 `running + owner pid 已不存在` 派生识别为 `interrupted`，诊断工具只读报告，下一次同 Workspace 运行可追加一条恢复说明，不改写旧事件。
- `.log` 只写可读的语义行，展开 attempt、engine、device、chunk、duration、exit code、error code；高频原始采样不得刷屏。
- API Key、Authorization、token、password、完整 prompt 和 `.env` 内容继续禁止写入任何日志。
- 诊断工具优先选择最近的失败 Step，而不是 run 汇总事件，并返回正确 owner、safe rerun step、上游成功 Artifact 和被阻塞步骤。

### 3.6 UI 两行独立状态合同

主界面日志区改为两个固定槽位，而不是最近 N 条历史：

- 第一行“当前业务”：例如“正在识别语音：Qwen3-ASR（第 2/169 段）”；
- 第二行“进度/处理建议”：正常时显示真实进度、设备和 ETA，失败时显示业务原因及下一步操作。

UI 只消费一个经 Application 层投影后的状态流；完整 journal 事件不再同时作为第二套 UI 消息源。相同语义签名不重复刷新。错误正文通过 `step_id + error_code + diagnostics` 映射为业务表述，原始异常和 traceback 仅留完整日志。

“记住 API Key”使用主题无关的明确两态 indicator：未选为空框，选中为 `✓`；鼠标和空格键均可切换，继续只在用户勾选并保存时写本机 `.env`，保存不联网。

## 4. 执行阶段与门禁

### P0：冻结证据与日志 Schema（必须最先完成）

实施：为 runtime/attempt/chunk/error/interrupt 事件定义字段、错误码和脱敏规则；把本计划中的两个 Workspace 固化为只读回归样本描述，不复制视频、音频或密钥进入 tests。

门禁：

- 每个事件都有 run_id、step_id、type、code、level、timestamp、elapsed 和可选 attempt_id；
- `asr_model_loading` 不再归到 unknown/runtime；
- 对同一错误可从 JSONL 得到唯一首要失败 Step；
- 高频心跳与真实业务进度被明确区分。

### P1：补齐日志单写入者和诊断器

责任模块：`execution/events.py`、`scripts/diagnose_workspace.py`、`docs/diagnostics/problem-index.yaml`，以及必要的 Application 事件 DTO。

实施：增加 ASR 语义事件、人类可读细节、summary 限频检查点和 interrupted 派生判断；修正诊断失败选择算法与当前 Workspace 路径解析。

门禁：用当前 faster-whisper 日志回放时，报告必须定位 `transcript.decode`、非空错误码/owner、`safe_rerun_from=transcript.decode`；用当前 Qwen 日志回放时必须报告“运行被中断、最后活动阶段 transcript.decode、无终态”，不得误报仍在正常运行。

### P2：修复 faster-whisper 进程边界和模型链降级

责任模块：`asr.py`、`execution/steps/coarse.py`、Processing Request 到 ProcessingOptions 的编译路径。

实施：构造最小可序列化 worker payload；在启动前校验；按阶段分类 worker-start/CUDA/model/inference 错误；统一 `engine_chain`；记录每次尝试并在后备成功时返回 degraded。

门禁：

- 嵌套 terminology mapping 可通过 Windows spawn 参数序列化测试；
- process.start 前的序列化错误不会产生 `asr_cuda_fallback`；
- fake faster 失败、fake qwen 成功时只尝试两次、顺序正确、Step=degraded、下游可继续；
- 单模型失败时 UI 获得一个业务错误，journal 保留完整技术原因。

### P3：接通 Qwen runner 真实进度并据此决定性能修复

责任模块：`scripts/qwen_asr_runner.py`、`asr.py`、`progress.py`/ETA 投影层。

实施：runner 输出 environment/load/batch/chunk/final JSONL；父进程在线解析、校验单调性、写 attempt 日志；删除假进度公式；用官方 `qwen-asr` Transformers backend 替换静默 legacy 路径；实现与显卡型号无关的 capability probe、低峰值加载、无重复在线 batch 校准、速度熔断和队列内 worker 复用。

性能决策门：

- 若实际为 CPU：先修 runtime/GPU 能力识别并在 UI 明示，不做块参数“优化”；
- 若官方 backend 缺失或落到 legacy：启动失败并给出业务说明，开发验收不得把 legacy 性能算作完成；
- 若模型加载占短样本总耗时多数：启用一个可取消、可终止、仅在当前桌面进程存活期间复用的 worker；
- 若 GPU 单批实时率才是瓶颈：只对固定短样本执行一次 batch=1 与候选 batch 的 A/B 微基准后选择安全值；
- 通用最低放行线：滚动热态预测 RTF `<= 0.25`（至少 4 倍实时速度），冷态 30 秒内出现首个有效阶段事件；当前开发机还要求相对 legacy baseline 至少提升 2 倍。有效画像命中时可在首批后判断，否则至少取得两个热态批次；未达线即熔断并降级，不允许继续假装正常处理数小时；
- 任一优化不得让取消、单实例互斥、显存释放或每视频独立 Artifact 失效。

门禁：fake runner 的 batch/chunk 进度必须准确映射到音频秒数和 ETA；模型加载时不显示虚假百分比；完整日志数量随完成块数线性增长，而不是随 250 ms 轮询增长；官方 backend、实际 runtime、GPU、dtype、attention、实际 batch、峰值显存、profile 命中/失效、速度熔断和 OOM 降级均有可验证记录。

### P4：收敛 UI 事件源、业务错误和复选框

责任模块：`application/processing.py`、`desktop/controller.py`、`desktop/models.py`、`desktop/view.py`。

实施：Application 层把 journal 事实投影成唯一 UI 状态；View 使用两个独立槽位；集中错误呈现；将语音模型自由文本改为带说明的单选下拉框；为“记住 API Key”使用明确勾号 indicator。

门禁：下拉框只显示 `faster-whisper（高速）` 和 `Qwen3-ASR（方言）`，默认高速项且持久化内部稳定值；一次逻辑进度只更新一次快照；两行分别承担业务与详情且内容不相同；技术异常不直接占据业务行；勾选显示 `✓`、取消为空框，保存语义和云端 opt-in 不变。

### P5：集中回归与一次性验收

先运行以下最小责任测试，某项失败时只重跑该项，全部通过后才运行一次完整离线套件：

1. ASR worker payload/错误分类单测；
2. 双模型 fallback/degraded Step 测试；
3. fake Qwen runner 真实 batch/chunk 进度、官方/legacy backend 判别、OOM 有界降级、stderr 脱敏和取消测试；
4. capability matrix 参数化测试：无 CUDA、CUDA 算子失败、4/8/12/16GB、BF16/FP16、不同 compute capability、历史 profile 失效和低空闲显存；这些全部使用 fake capability，不要求准备多张实体 GPU；
5. 在线 batch `1 -> 2 -> 4` 不重复处理、收益停止、OOM 减半、RTF 熔断和队列复用/卸载测试；
6. journal summary/interrupt/diagnose 回放测试；
7. UI projector 两行去重、业务错误映射、语音模型下拉映射和 checkbox 状态测试；
8. 15 步 DAG、缓存、Document v2、桌面控制既有相关回归；
9. 完整离线测试套件只运行一次。

完整套件通过后，才申请真实本地模型烟测授权：

- faster-whisper：一个短音频，只验证 spawn、设备分类、真实完成和日志；
- Qwen3-ASR：一个覆盖多个 60 秒块的固定短音频，先测 legacy baseline，再仅测一次候选 batch，验证官方 backend、GPU 与动态 BF16/FP16、load/batch/chunk/ETA、完成、RTF 和显存释放；
- 两个烟测覆盖不同责任，不重复跑完整知识、VLM、Word/PDF 链；
- 2 小时 48 分的“高数”长视频不作为 V4.2 常规验收，只有短烟测仍无法解释规模问题时再单独申请长视频重跑授权。

本升级不需要真实云端请求、模型下载、长视频重跑或多次全量测试。由于当前 bundled runtime 缺少官方 `qwen-asr` 包，进入 P3 前必须单独取得一次“更新隔离 ASR runtime 依赖”的授权；只补齐并冻结所需运行库，不覆盖现有模型权重，也不在应用运行时联网安装。

## 5. 验收标准

V4.2 只有同时满足以下条件才算完成：

- faster-whisper 不再因 `mappingproxy` 在 spawn 前失败，也不再把非 CUDA 错误伪装成 CUDA 降级；
- UI 本地语音模型是单选下拉框，两个显示项、默认值、内部值和失败自动降级说明均准确；
- 下拉首选失败时可真实切换后备，成功后全链路继续并明确标记 degraded；
- Qwen3-ASR 使用官方 Transformers backend、GPU 上按能力选择 BF16/FP16 并自适应 batch，展示并记录真实加载/批次/块进度，能够用日志回答“实际 runtime、设备、加载多久、每批多久、卡在哪一块”；
- 策略不含 4060/5060/5070 型号分支；fake capability matrix 全部通过，换卡或 runtime 变化会自动重建画像；
- 当前开发机验收样本达到热态 RTF `<= 0.25`、相对 legacy 至少 2 倍提升，冷态 30 秒内出现首个有效进度；其他机器以同一 RTF/冷态门禁自校准，未达线自动降级；
- 每个 run 有可重建的完整 JSONL、可读日志和一致 summary；外部中断不会永久伪装为正常 running；
- 只读诊断能准确返回失败 Step、错误码、owner 和局部重跑点；
- UI 只有两行独立信息，无四路重复；错误是业务语言，完整技术细节仍可追踪；
- “记住 API Key”选中态为勾号，保存和授权边界不变；
- 既有 15 步、缓存、云端 opt-in、VLM、聚合、拖动排序、单实例、清缓存、Markdown/Word/PDF 和本地回看无回归；
- 完整离线套件一次通过，真实本地模型烟测在另行授权后各一次通过。

## 6. 兼容、迁移与回滚

- 不迁移、不删除历史 Workspace；旧 schema 日志继续只读，诊断器兼容缺少 attempt 字段的 v1 事件。
- 新日志字段仅追加，不改变 Artifact 或 Document v2；已有有效缓存继续命中。
- 新 UI 投影失败时可回滚 Application/View 层，不影响 journal 和执行内核；ASR 进程合同与错误分类可以独立回滚。
- 不把当前两个取证 Workspace 当作可写测试目录；测试临时数据只放 `tmp/` 或测试临时目录。
- 实施前保存当前 dirty worktree 边界；不覆盖已有打包相关改动，不读取、输出或提交 `.env`。

## 7. 本轮明确不做

- 不用增加日志频率代替语义完整性；
- 不硬编码“Qwen 一定慢”或“CUDA 一定坏”的结论；
- 不擅自改变用户未选择的 ASR 模型顺序；
- 不为这次修复改变知识模板、大模型责任边界或云端预算；
- 不重跑“高数”长视频，不发起云端请求，不下载或替换模型；
- 本计划获批后只回填一次 V4.2 时间线；实施、验收或交付不得再追加同版本记录。

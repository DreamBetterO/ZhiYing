# 迭代记录与问题

本文件只在用户明确批准版本后追加；一个版本一条，仅包含时间、版本、版本类型、用户发现的问题和最终确定的解决方案。

---

## 2026-08-06（Asia/Shanghai）｜V1｜大版本功能迭代

### 发现的问题

- 原工程主要依赖一条通用提示词直接生成全文，缺少课程画像、内容鉴别、知识分类和针对不同知识类型的整理策略。
- 知识整理逻辑集中在原有总结模块中，不利于持续调整知识选择、详略和自检方式。

### 确定的解决方案

- 从总结模块中抽离独立 knowledge 层，按 schema、课程画像、内容选择、专业化整理、轻量自检、适配和流水线划分职责。
- 将知识处理固定为“课程画像 → 内容鉴别 → 专业化整理 → 轻量自检 → 文档适配”，不同知识类型使用对应整理策略。
- `build_document` 优先使用知识流水线，并保留旧总结路径作为兼容回退。

## 2026-08-07（Asia/Shanghai）｜V2｜大版本功能迭代

### 发现的问题

- 第一轮知识流水线仍缺少课程级规划，知识点轻重、讲解结构和图片需求没有统一合同。
- 图片与知识点之间缺少明确的视觉语义绑定，容易退化为按附近语音或时间选择图片。
- 正文、步骤、提示、图片和图注缺少统一内容块，Markdown、Word 和 PDF 难以保持一致排版。

### 确定的解决方案

- 增加 `LessonPlan`，合并课程画像、内容选择和知识点规划，让 organizer 按知识点计划生成讲义。
- 增加 `FrameSemantic` 与 `VisualBinding`，图片只能通过显式绑定进入知识点，删除无条件使用最近时间图片的逻辑。
- 增加 `content_blocks`，统一正文、步骤、提示、图片和图注在 Markdown、Word、PDF 中的块级渲染。
- 保留聚合文档的来源时间戳，并让 Word 图片按原比例缩放，避免固定尺寸拉伸。

## 2026-08-10（Asia/Shanghai）｜V2.1.1｜小版本修正

### 发现的问题

- 当前输出存在图片重叠、近似图片重复使用和图文不对应。
- 图片仍可能依赖时间戳和附近语音匹配，而不是真实图片内容。
- 旧图片绑定与新视觉证据可能同时供图，图注、解释和图片可能重复或拆散。

### 确定的解决方案

- 让 `VisualEvidence` 成为整任务唯一图片权威；旧图片绑定只保留整任务级兼容回退，不与新证据混用。
- 时间戳只负责召回、排序和来源回链；没有 OCR/VLM 等像素证据时必须 `no_match`。
- 通过图片哈希、近似相似度和短时间邻域建立场景簇，再进行课程级仲裁；同一场景默认只渲染一次。
- 将导语、图片、唯一图注、解释和时间回链组成不可拆散的 `visual_group`，统一 Markdown、Word 和 PDF 的视觉呈现。

## 2026-08-10（Asia/Shanghai）｜V2.2｜小版本功能迭代

### 发现的问题

- 强 PPT、图表分析和软件教学需要更多有效图片及更深入的图片解释，现有图片数量和图文配合仍不足。
- 图文应互相服务；不能先按时间选图再为图片补文字，也不能只提高截图数量阈值。
- 内容“精简/推荐/丰富”同时控制正文和图片，不利于表达“正文精炼但图解丰富”等真实需求。
- 知识点轻重和讲解深度仍需前置判断；不同知识类型不能共用同一展开模板。
- Qwen3-VL-2B 可能存在小字、密集界面、多图比较和复杂推理局限，方案需要在本机资源内合理使用模型，而不是简单堆叠技术。

### 确定的解决方案

- 内容详略与图文教学解耦，新增“图文教学：自动/精简/均衡/增强”。
- 在课程规划阶段生成课程视觉画像，并为每个知识点确定视觉职责、视觉问题、成功条件、图片数量上限、组图方式和解释深度。
- 沿用场景聚类，OCR 只处理 canonical frame 和目标时间窗；语音知识点、OCR、场景类型和时间弱先验共同召回候选。
- Qwen3-VL-2B 只负责最多 4 张候选的比较/拒绝，以及 1 张入选图片或 ROI 的细节证据提取；不负责课程规划、知识扩写或最终写作。
- 图片文字优先由轻量 OCR 提取，VLM 负责判断文字、区域、走势和知识问题之间的关系。
- 写作器只消费已确认的视觉证据，并按定位、解释、步骤、对比、证据和回顾等职责生成教学型图解。
- OCR/VLM 不可用、输出无效或资源不足时安全返回 `no_match`；不恢复时间最近帧，不静默调用云端。
- 保留现有顺序流水线和 JSON → Markdown → Word → PDF，不在本版本引入 LangGraph、全视频 VLM、向量库或更大的本地视觉模型。

## 2026-08-10 17:49（Asia/Shanghai）｜V2.2｜小版本功能迭代｜已验证

### 发现的问题

- 真实本地 VLM 烟测发现，旧 `VisualEvidence` 缓存签名未包含 runtime/python/runner，runtime 路径修正后仍可能复用旧 `no_match`。
- Qwen3-VL 会把 JSON 模板中的占位说明复制到 `criteria_met`，也可能把成功条件原文复述为 `visible_evidence`。
- 个别 detail pass 会返回非法 JSON，不能作为可靠兜底。

### 确定的解决方案

- `VisualEvidence` 缓存版本升至 5，并把本地 VLM runtime/python/runner 纳入签名。
- 本地 VLM prompt 改为字段语义说明，不再在 JSON 示例里放可复制占位文本。
- 过滤“成功条件原文”类伪证据；当 `visual_answer` 明确包含图像、标注、箭头、K线等画面线索时，允许作为备用可见证据。
- detail pass 失败时保持 `no_match`，不采用无法结构化验证的粗选结果。

### 验证结果

- `test4-1` 与 `test4-2` 的缓存流程、QA VLM 烟测和 Markdown/Word/PDF 渲染已通过；两个样例各产生 1 条 `VisualEvidence select` 与 1 个知识点内 `visual_group`。
- 本地 VLM 烟测未走云端，`cloud_tokens=0`；峰值显存约 7071 MiB。
- 完整单测 159 项通过；Python 编译、Node 渲染脚本语法、YAML 解析、`pip check` 和 `git diff --check` 通过。

### 未解决项

- 本地 Qwen3-VL 仍为短生命周期子进程，加载开销较大。
- OCR 未在本次样例中启用；小字和密集行情界面后续仍需 OCR + VLM 组合验证。

## 2026-08-12 10:04（Asia/Shanghai）｜V3.0｜大版本升级

### 发现的问题

- 本地 VLM 按视觉问题逐条启动并重复加载模型，处理速度慢，视觉任务和候选场景又可能在推理后才被丢弃。
- 正常的证据拒绝、候选不足和场景去重曾被表现为 VLM“失效”，上游残缺问题与单图/多图合同不一致也造成大量无效调用。
- 剩余时间按全局百分比线性外推，与 ASR、视觉、云端和渲染的真实工作量不匹配，且长阶段内不会持续更新。
- 规划、视觉、正文、云端精炼和渲染缺少统一中间合同，整体工作流重复、低效且难以持续扩展。
- 本地整理把同一课堂句子同时写入标题、正文段落、规则/步骤列表和兼容字段，导致产出文档重复。
- 云端精炼输入包含冗长且重复的课程计划与视觉上下文，输入格式和本地图片信息如何交给云端缺少明确边界。

### 确定的解决方案

- 建立统一 `CourseIR` 与 Canonical Document v2，让来源、知识单元、原子 Claim 和视觉证据成为规划、整理、校验与渲染的共同合同，并保留 v1 迁移与回滚路径。
- 本地正文先建立带来源的 Claim 台账，再互斥路由到 paragraph、rule_list、steps、example、pitfall 和 visual_group；增加标题校验与确定性去重门，原始转写和回看链路保持不变。
- 视觉任务在推理前完成问题合同校验、作业总预算和场景预约；每个视频只加载一次本地 VLM，逐任务保存与缓存，默认不并行大 batch。
- 将证据不足等正常结果记为 expected no_match；只有超时、OOM、runner 崩溃和协议非法等真实推理失败才在任务级汇总一次 warning。
- ETA 改为基于 ASR 音频进度、视觉作业数、云端批次和渲染子阶段的任务估算；无依据时显示“估算中”，有依据后按 deadline 持续倒计时。
- 云端不接收 Markdown、PDF、完整 document.json 或默认图片像素；由 `CourseIR` 构造紧凑 JSON 投影，只发送必要来源、知识计划和已核实的视觉 ID/事实，云端返回引用 ID，本地再解析图片并生成 Markdown、Word 和 PDF。

## 2026-08-12 17:18（Asia/Shanghai）｜V4.0｜大版本架构升级

### 发现的问题

- 用户提出问题并确定方案后，Agent 难以完整执行和持续优化；出现新问题时仍需长时间重新查找，问题定位不够稳定、精确。
- 项目迭代容易遗留僵尸代码、重复兼容路径和不断复杂化的简单逻辑，影响效率与长期维护。
- 主流水线、知识整理、`summarize` 和部分脚本职责过度耦合，流程状态、缓存、运行服务与业务算法混在一起。
- 工程中间件和中间产物也存在耦合：外部工具/模型由业务代码直接初始化，Workspace 路径、JSON Schema、缓存签名和上下游失效规则分散维护。
- Desktop 同时承担 Tk 界面、队列状态、后台执行、云端配置、缓存清理、聚合和结果处理，难以独立测试和安全迭代。
- 项目需要更清晰的记忆入口、模块边界、故障定位索引和执行清单，使个体项目保持干净、稳定，并具备非 demo 级持续开发能力。

### 确定的解决方案

- 建立 V4.0 可恢复执行内核，以 `ProcessingContext + PipelineStep + PipelineRunner + ArtifactStore + WorkspaceCache` 为核心，统一步骤状态、依赖图、缓存决策、选择性失效、原子提交和局部重跑。
- 通过显式 ports 和唯一 composition root 隔离 ffmpeg、ASR/VLM 子进程、云客户端、Node/Word/PDF 等中间件；缓存判定完成前不得初始化昂贵能力。
- 为所有中间产物建立稳定 Artifact ID、WorkspaceLayout、Schema 校验、指纹和 CacheRecord，业务模块不再直接拼路径、读写他人 JSON 或自行维护缓存。
- 拆分 `summarize` 的文本、离线文档、SourceBlock、Document 和编排职责，以知识 DAG 替代完整执行与局部恢复两套流程；稳定后删除旧云端大提示词、无生产调用模块、旧开关和迁移桥。
- 增加 Application Service，并将 Desktop 解耦为可脱离 Tk 测试的 Controller/状态机、纯 Tk View、设置/凭据边界和公开 DTO；后台线程不得直接操作 Tk，View 不接触 Runner、Artifact、provider 或 Workspace JSON。
- 建立单一 Agent 执行入口、当前状态、模块边界、Step/Artifact 索引、稳定错误码、只读 Workspace 诊断和架构守卫测试；升级按阶段收敛门、回滚门和删除门实施，保持 JSON → Markdown → Word → PDF、Document v2、时间戳与 `video-study://`。

## 2026-08-14 10:48（Asia/Shanghai）｜V4.1｜小版本升级

### 发现的问题

- 云端与聚合链路存在响应截断、请求额度被失败重试耗尽、成功批次不能恢复，以及云端失败后无法稳定完成聚合产物的问题。
- 云端精炼资料存在口语、重复、详略不当和课程资料感不足；固定模板和门禁限制过多，用户配置又过于繁琐。
- 聚合未成为本地/云端主流程中的统一模式，队列顺序调整、聚合状态和最终产物入口不符合实际使用方式。
- Desktop、CMD 和 CLI 任务缺少全局互斥，可能同时抢占模型、GPU 和文档资源。
- 所选视频的 Workspace、Output、派生聚合结果和产物按钮缺少一致、准确的清理与可见性控制。

### 确定的解决方案

- 使用自动加载的自然语言 Markdown“课程资料整理偏好”表达文档组织思路、关注重点和表达要求，不增加复杂配置；现有规划调用形成可审计的编辑决策，现有精炼调用执行该决策，大模型自主决定结构与详略，程序只保留来源、完整性、预算和安全硬门。
- 增加云端截断分类、输出感知分批、逐批检查点和恢复；云端聚合失败时降级为真实本地聚合，且聚合精炼正文成为 Document v2 权威，不再被来源原始正文覆盖。
- 将聚合改为可开启/关闭的本地与云端处理模式，按队列顺序自动完成单视频处理和最终聚合；用鼠标拖动替代上下移动。
- 为 Desktop 与 CLI `run` 增加 Windows 全局单实例互斥，并保留 Workspace 第二层锁；`doctor` 和 `video-study://` 本地播放不受阻。
- 将操作统一为“清除所选缓存”，安全清除所选 Workspace、Output 和失效派生聚合结果并保留原视频；Markdown、Word、PDF 和聚合入口仅在对应文件完整生成后显示。
- 按责任模块设置唯一主测试和阶段门禁，复用既有缓存与离线 fixture，不重复长视频、真实 VLM、相同产物或无授权云端测试，并保持现有 15 步、CourseIR、Document v2、JSON → Markdown → Word → PDF、时间戳与 `video-study://` 能力不受损。

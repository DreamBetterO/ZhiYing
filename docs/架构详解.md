## 1. 总体架构与分层

系统采用六边形架构（Hexagonal Architecture），核心原则是**业务逻辑不依赖具体模型/外部服务实现**，所有外部能力通过端口（Port）注入。

```
┌─────────────────────────────────────────────────────────┐
│                     桌面端 (desktop/)                     │
│   DesktopController（状态机） ←→ Tk View（UI 渲染）        │
│              ↓ 只调用 Application Service                  │
├─────────────────────────────────────────────────────────┤
│                   应用层 (application/)                   │
│   ProcessingService · ProcessingRequest · ProcessingHandle│
│              ↓ 编排                                     │
├─────────────────────────────────────────────────────────┤
│                   执行层 (execution/)                     │
│   ProcessingContext → StepRegistry → PipelineRunner      │
│        → ArtifactStore（原子写入） → WorkspaceCache       │
│              ↓ 调度 15 个 Step                             │
├─────────────────────────────────────────────────────────┤
│              知识子系统 (knowledge/)                     │
│   规划 → 视觉证据 → CourseIR → 整理 → 自检 → Document v2  │
├─────────────────────────────────────────────────────────┤
│                端口与适配器 (ports + adapters)            │
│   MediaPort · SpeechPort · VisionPort · CloudJsonPort    │
│   DocumentPort —— 具体实现惰性构造，不提前加载模型          │
└─────────────────────────────────────────────────────────┘
```

### 分层边界（`module-boundaries.yaml` 校验）

| 层 | 模块 | 允许依赖 | 禁止依赖 |
|---|---|---|---|
| 应用层 | `application` | execution, aggregate, config | tkinter, knowledge, openai, subprocess |
| 桌面层 | `desktop` | application, desktop.models, desktop.settings | knowledge, providers, execution.runner, subprocess, openai |
| 执行层 | `execution` | execution, progress | tkinter, openai, subprocess |
| 知识层 | `knowledge` | knowledge, transcript, execution.task_groups | desktop, pipeline, tkinter, subprocess, openai |
| 端口层 | `execution.ports` | execution.contracts | desktop, tkinter |
| 渲染层 | `render` | document.v2, localplay | desktop, providers, knowledge.planning, openai |

关键约束：**桌面层不直接依赖知识层或 providers**，所有模型调用必须经过 Application → Execution → Port 链路。这确保 UI 线程永远不会直接持有模型引用。

### 组合根（Composition Root）

`execution/bootstrap.py` 中的 `build_runtime_services` 是唯一的依赖注入点：

- 所有 Port 工厂注册为**惰性单例**（`RuntimeServices.port(name)` 首次调用时构造，线程锁保护）。
- `cloud` Port **仅在** `RunPolicy.cloud_authorized=True` 时注册；未授权时构造和请求均为 0。
- `vision` Port 在 `open_session` 时才执行预检（preflight），预检失败不阻塞流水线。
- 用户传入的 `ProcessingOptions` 经过 `_secret_field_path` 过滤，任何含 `api_key`/`password` 的字段被拒绝。

## 2. 15 步流水线详解

```
source.probe
├─ audio.extract → transcript.decode → transcript.normalize
└─ frames.candidates → frames.select
   transcript.normalize → knowledge.plan
   knowledge.plan + frames.select → visual.jobs → visual.evidence
   transcript.normalize + frames.select → frames.semantics
   knowledge.plan + visual.evidence → knowledge.course_ir
   CourseIR + plan + evidence + semantics → knowledge.units → knowledge.selfcheck
   全部知识 Artifact → document.assemble → Canonical Document v2
   Document v2 → render.bundle → Markdown → Word → PDF
```

### 2.1 媒体探测与提取（Coarse Steps 1–6）

#### `source.probe` — 源探测
- **输入**：无（从 `ProcessingContext.source.path` 获取视频路径）。
- **输出**：`source.manifest`（JSON，含 duration、size、fingerprint）。
- **机制**：通过 `MediaPort.probe` 调用 ffprobe，获取视频时长、文件大小，计算内容指纹。
- **指纹**：`source.fingerprint + size_bytes`。
- **降级**：无（失败即终止）。

#### `audio.extract` — 音频提取
- **输入**：`source.manifest`。
- **输出**：`audio.flac`（16 kHz 单声道 FLAC）。
- **机制**：`MediaPort.extract_audio` 调用 ffmpeg，将 MP4 转为 16 kHz 单声道 FLAC。
- **remote_cost**：`LOCAL_HEAVY`（本地计算密集）。
- **缓存**：文件存在则跳过。

#### `transcript.decode` — 语音识别
- **输入**：`audio.flac`, `source.manifest`。
- **输出**：`transcript.raw`（带时间戳的原始文本段 JSON）。
- **机制**：执行**引擎链回退**——按配置的 `engine` 选择 faster-whisper 或 Qwen3-ASR，主引擎失败时自动降级到备用引擎并记录 `fallbacks`。
- **remote_cost**：`LOCAL_HEAVY`。
- **降级**：见 [5.1 ASR 降级](#51-asr-降级)。

#### `transcript.normalize` — 转写规范化
- **输入**：`transcript.raw`, `source.manifest`。
- **输出**：`transcript.normalized`（规范化 JSON）+ `transcript.srt`（BOM UTF-8 SRT）。
- **机制**：两步纯函数变换——
  1. `clamp_segment_timestamps`：将所有段时间戳钳制到 `[0, duration]` 范围内。
  2. `apply_terminology_corrections`：按 `terminology_replacements` 配置（如 `残嫩→缠论`），使用最长优先的非级联正则替换误识别词，保留 `raw_text` 和 `applied` 记录。
- **降级**：无（纯函数，不会失败）。

#### `frames.candidates` — 帧候选提取
- **输入**：`source.manifest`。
- **输出**：`frames.candidates`（候选帧 JSON + 图片目录）。
- **机制**：`MediaPort.extract_frame_candidates` 调用 ffmpeg，按 `fps=1/interval`（默认 10 秒/帧）+ `scale=max_width(1280):-2` 采样，上限 600 帧。interval 自动下取整 `duration/max_candidates` 防止溢出。
- **remote_cost**：`LOCAL_HEAVY`。

#### `frames.select` — 关键帧筛选
- **输入**：`frames.candidates`, `transcript.normalized`, `source.manifest`。
- **输出**：`frames.selected`（精选关键帧 JSON + 写入 workspace 的图片）。
- **机制**（四阶段算法）：
  1. **内容缩略图**：灰度裁剪（丢弃 10% 水平边缘 + 14%/15% 垂直边缘以去除播放器 UI），缩放至 128×72。
  2. **场景聚类**：按像素差异（ImageChops 平均差/255）≥ `scene_change_threshold`（默认 0.025）迭代分组；跳过 `content_start_padding_seconds`（默认 30s）之前的帧。
  3. **代表选择**：每个场景取最大 Shannon 熵的帧作为代表，仅熵 ≥ `min_content_entropy`（2.4）的帧入选（回退：全局最大熵帧）。
  4. **分箱**：若入选帧 > `max_keyframes`（8），将有效时间线分箱，每箱取最高熵帧，保证最小间隔 `min_keyframe_gap_seconds`（480s），再按熵值补足。
- **关键设计**：`frames.select` 依赖 `transcript.normalized`，使关键帧选择与转写内容对齐——这是模态融合的第一个交汇点。

### 2.2 知识整理（Knowledge Steps 7–14）

#### `knowledge.plan` — 课程规划
- **输入**：`transcript.normalized`。
- **输出**：`knowledge.plan`（LessonPlan JSON，含章节、知识单元、视觉需求、深度合同）。
- **能力**：`offline` + `cloud`；`degradation_policy="offline"`。
- **离线模式**（`plan_offline`，版本 8）：
  1. 合并 ASR 段（180 字 / 45 秒）→ 关键词 bigram → 120 秒间隔分章。
  2. 每个合并行生成 `UnitPlan`，按关键词线索推断知识类型（concept/rule/procedure/mechanism/comparison/case/conclusion）。
  3. **领域识别**：`_match_domain` 对 top-30 术语评分，匹配金融技术分析/医学/软件操作/法律等领域。
  4. **形态识别**：`_match_form` 根据口语线索匹配 5 种课程形态。
  5. **视觉画像**：`_infer_visual_profile` 统计图表/屏幕/幻灯片/指认等术语，输出 `VisualProfile`（chart_analysis/screen_demo/slide_dominant/mixed/speech_dominant），含视觉依赖度和推荐级别。
  6. **深度合同**（`_assign_depth_contracts`）：计算 5 维深度因子（依赖性/难度/错误风险/来源容量/迁移价值），按优先级 `3·dep + 2·diff + 2·err + trans` 排序，按详略档位（精简 .15 / 推荐 .28 / 丰富 .38 比例）分配 `detail_level`（mention/brief/standard/deep）和 `target_chars`。
  7. **视觉合同**：`_visual_contract` 根据类型选择角色（procedure/compare/evidence/locate/recap/explain），生成 `success_criteria`（必须是像素可验证的，禁止"能否回答问题"类抽象条件）和 `visual_questions`（每单元最多 1 个主问题，总上限按时长×级别因子截断）。
- **云端模式**（`plan_cloud`）：构建源文本块 → 渲染规划 prompt → `cloud_port.request_json_with_info` → 严格校验（章节数 ≤16、plan_id ≤64、标题非空、来源引用有效）。失败时回退到离线模式。

#### `visual.jobs` — 视觉任务收集
- **输入**：`knowledge.plan`, `frames.selected`, `transcript.normalized`。
- **输出**：`visual.jobs`（待执行的视觉比对任务列表）。
- **机制**：`collect_visual_jobs` 从 plan 的 `visual_questions` + `visual_contracts` 构建 compare 任务，受 `max_compare_jobs` 和 `vlm_compare_max_candidates`（≤4）限制。每个问题经过 `validate_visual_question` 校验——拒绝非像素可回答的、含代词/片段的、抽象的（如"重要性是什么"）、单帧模式下要求多帧对比（"前后变化"）的、缺少 `success_criteria` 的问题。**每知识点最多 1 个主问题**。

#### `visual.evidence` — 视觉证据检索
- **输入**：`visual.jobs`, `knowledge.plan`, `frames.selected`, `transcript.normalized`。
- **输出**：`visual.evidence`（视觉证据 JSON，含选中帧、可见证据、满足/未满足标准）。
- **机制**（四阶段流水线，证据版本 11）：
  1. **候选召回**（`recall_candidates_for_question`）：先按场景聚类（`cluster_visual_scenes`），再按 `content_score×0.8 + time_prior×0.2`（`time_prior = 1/(1+dist/60)`，时间作为弱先验）对每场景的代表帧评分。可选 OCR 重排（`_targeted_ocr_rerank`）：对召回帧运行 OCR，按语义召回分数（OCR 命中率 × 内容分 × 场景类型线索 × 时间先验）重排。
  2. **VLM 比对**（`_vlm_select`）：调用 `provider.compare_candidates(question, candidates, contract)`，VLM 从候选帧中选择满足所有 `success_criteria` 的帧。提取 `visible_evidence`，将报告标准与合同文本交叉验证（SequenceMatcher ≥0.78）。
  3. **细节复核**（可选 `detail` pass）：对选中帧执行第二趟 `provider.extract_selected`，提取更详细的可见信息。compare → detail 顺序执行，detail 次数 < 2。
  4. **仲裁**（`arbitrate_visual_evidence`）：每场景最多 1 个主证据（DFS 去重），输掉的证据折扣化，强制每单元 `max_count` 预算。`sanitize_visual_evidence_for_reader` 剥离 A/B/C/D 候选别名。
- **VLM 会话模型**：每视频**单会话**，模型只加载一次。首个未命中任务触发冷加载（`start_session`），后续任务复用同一子进程。OOM 时重试 2 帧候选；会话失败重启一次后批次熔断。
- **降级**：见 [5.3 VLM 降级](#53-vlm-降级)。

#### `frames.semantics` — 帧语义标注
- **输入**：`frames.selected`, `transcript.normalized`。
- **输出**：`frames.semantics`（关键帧的语义标注 JSON）。
- **机制**：`build_frame_semantics` 为每个关键帧生成语义标注——关联最近的转写段、推断帧类型（slide/code/demo/diagram/other）、提取 OCR 文本（如启用）。用于后续知识整理中图片的上下文增强。

#### `knowledge.course_ir` — Course IR 生成
- **输入**：`knowledge.plan`, `transcript.normalized`, `visual.evidence`。
- **输出**：`knowledge.course_ir`（CourseIR JSON）。
- **机制**（版本 1）：
  1. `build_source_blocks`：合并转写段为稳定 ID（`block_NNNN`）的源块，重复块标记 `adds_new_information=False` 并关联 `canonical_source_id`。
  2. `build_course_ir`：每个 plan unit → `CourseUnit`；将转写句子拆分为 claims（step/example/pitfall/condition/conclusion/explanation），按 SHA-256 指纹去重（同句不同源追加 `source_ids`），标记 `origin="audio_backed"`。视觉证据仅取 `decision=="select"`。
  3. `route_claims_to_blocks`：按 `display_block`（paragraph/rule_list/steps/example/pitfall）将 claims 路由为 `ContentBlock`。
  4. `course_ir_to_units`：生成 `KnowledgeUnit`（含 `content_blocks`、`evidence_refs=[{segment_ids, frame_ids}]`、`facet_status`、`visual_group` 块 + 可选 `understanding_tip`）。
- **去重**：exact 去重（SHA-256 指纹）+ containment 去重（句子包含检测）+ near-duplicate 报告（SequenceMatcher ≥0.88，差异含数字/否定时不删）。

#### `knowledge.units` — 知识单元整理
- **输入**：`knowledge.plan`, `knowledge.course_ir`, `frames.semantics`, `visual.evidence`, `transcript.normalized`。
- **输出**：`knowledge.units`（整理后的知识单元 JSON）。
- **能力**：`offline` + `cloud`；`degradation_policy="offline"`。
- **离线模式**：`build_course_ir` → `course_ir_to_units` → `run_dedup_gate`。
- **云端模式**（`organize_cloud`）：
  1. `build_cloud_payload` 将 CourseIR 投影为紧凑载荷（见 [7.2 紧凑载荷](#72-紧凑载荷)）。
  2. `plan_payload_batches` 按 token 上限分批。
  3. 每批调用 `cloud_port.request_json_with_info`，prompt 要求按写作计划逐项整理。
  4. `_validate_organizer_payload` 严格校验：plan_id 全覆盖、statement/explanation 非空、source_block 引用有效且归因正确、content_blocks 可渲染。
  5. 跨批聚合 document_title/overview/objectives/review/checklists。
  6. 失败时回退离线整理。
  7. 最终执行 `run_dedup_gate`。
- **降级**：见 [5.4 云端知识降级](#54-云端知识降级)。

#### `knowledge.selfcheck` — 知识自检
- **输入**：`knowledge.units`, `knowledge.plan`, `transcript.normalized`, `frames.selected`。
- **输出**：`knowledge.selfcheck`（SelfCheckReport JSON）。
- **机制**（V2，确定性检查，不调用模型）：
  - `source_existence`：核心知识点缺少 segment → error；缺少 frame → warning。
  - `direction_words`：源文本含方向/否定词但整理结果丢失 → warning。
  - `facet_status`：验证 facet 状态合法性。
  - `expand_completeness`：deep/standard 规则缺少条件/步骤/边界 → warning。
  - `visual_evidence`：标记了 `visual_or_formula` 但无帧 → "needs review"。
  - `plan_coverage`：未知 plan_id 或未覆盖 → error/warning。
  - `conflict`：同标题相反结论 → 标记 unresolved。
  - `binding_basis`：无效帧/单元引用 → error；仅时间依据 → warning。
  - `understanding_tip`：多 tip 或占比 >10% 正文 → warning。
  - `soft_quality`：标题/正文重叠、口语填充词密度过高、详略分布不均 → warning。
- **通过条件**：`errors == 0`。

#### `document.assemble` — 文档组装
- **输入**：`knowledge.units`, `knowledge.selfcheck`, `visual.evidence`, `knowledge.plan`, `frames.semantics`, `frames.selected`, `transcript.normalized`, `source.manifest`。
- **输出**：`document.v2`（Canonical Document v2 JSON）。
- **机制**：`units_to_document` 将知识单元组装为 Document v2，合并 cloud_info（token 用量/模型/降级原因），嵌入 `knowledge_pipeline` 运行时元数据。若无 units（如纯离线降级），使用 `build_offline_document` 回退。
- **Schema v2 核心**：`content_blocks` 是正文**唯一事实源**，`source_refs` 保存 segment、时间和 `video-study://play/<video_id>?t=<seconds>` 链接。Markdown/Word/PDF 通过只读兼容 view 消费同一 v2。

### 2.3 渲染（Coarse Step 15）

#### `render.bundle` — 三端渲染
- **输入**：`document.v2`。
- **输出**：Markdown + Word (.docx) + PDF（存储在 `output/` 目录）。
- **机制**：
  - **Markdown**：`render_markdown` 直接从 Document v2 的 `content_blocks` 生成。块类型包括 paragraph/visual_lead_in/rule_list/steps/example/pitfall/visual_group（含图片+看图重点）/understanding_tip/source_links（渲染为 `[▶ 回看来源·label](url)` 超链接）。回退兼容 v1 的 explanation + details/steps 列表。
  - **Word**：`render_docx` 通过 Node.js + docx-js（`scripts/render_docx.mjs`）渲染。完整消费 content_blocks 树，支持内联缩放图片、自定义微软雅黑样式、项目符号编号、A4 页边距、页眉页脚页码。
  - **PDF**：优先使用本机 Microsoft Word COM（`Word.Application.ExportAsFixedFormat`，格式 17）导出；失败时使用 reportlab 回退渲染（注册 msyh.ttc/simhei.ttf/simsun.ttc 中文字体，完整 content_blocks flowables，含缩放图片和页脚）。

## 3. 各模型工作方式与模块边界

### 3.1 ASR — 语音识别

| 维度 | faster-whisper（默认引擎之一） | Qwen3-ASR-0.6B |
|------|------|------|
| 实现方式 | `multiprocessing.spawn` 隔离子进程 | `subprocess.Popen` 调用 `scripts/qwen_asr_runner.py` |
| 运行环境 | .venv | 独立 conda 环境（ImageT10） |
| 设备 | `auto` → 优先 CUDA，失败降级 CPU | `cuda:0` 或 `cpu` |
| 计算精度 | CUDA: `int8_float16`；CPU: `int8` | bf16/f32 |
| 时间戳精度 | 段级（`word_timestamps=False`） | 块级（`timestamp_precision="chunk"`），块=60s |
| VAD | `vad_filter=True`，`min_silence_duration_ms=500` | 无 |
| 解码参数 | `beam_size=5`，`language=zh`，`condition_on_previous_text=True` | `max_new_tokens=768` |
| 热词 | `_initial_prompt` 合并 hotwords + 视频标题 | 无 |
| 进度上报 | `multiprocessing.Pipe` 实时段进度 | 基于单调时钟的时间估算 |
| 取消 | 终止子进程 | 终止子进程 |

**模块边界**：
- 定义：`execution/ports.py` → `SpeechPort`（`probe_capability`, `decode`）。
- 适配器：`execution/adapters/` → `SpeechAdapter`，封装 `asr.py` 的 `decode_audio`。
- 配置：`config.yaml` → `asr.*`（engine, model_id, device, beam_size, qwen_*）。
- 纯函数：`transcript.py` 的 `normalize_transcript` 不依赖任何模型。

### 3.2 VLM — 视觉语言模型

| 维度 | 值 |
|------|------|
| 模型 | Qwen3-VL-2B-Instruct |
| 运行环境 | 独立 conda 环境（ImageT10） |
| 设备 | **仅 CUDA**（预检不含 CPU 回退） |
| 加载方式 | `QwenVLSession` 短生命周期子进程，每视频单会话 |
| 会话协议 | 临时目录 JSON 文件交换（`ready.json` → `request-{id}.json` → `result-{id}.json` → `done.json`） |
| 两种操作 | `compare`（多帧选择）→ `detail`（单帧细节提取） |
| 生成参数 | `max_new_tokens` 受控，greedy（no_sample），`repetition_penalty=1.08`，`no_repeat_ngram=6`，`max_time=55`（防病态重复） |
| 像素预算 | min 256×28²，max = `visual_tokens`×28² |
| 输出恢复 | fence 剥离 → 尾逗号修复 → `ast.literal_eval` 回退 → `_repair_structured_result` 截断修复 |
| 原子写入 | `_atomic_json`（temp + replace） |
| 调试 | `VIDEO_STUDY_VLM_DEBUG_RAW=1` 保存原始输出 |

**模块边界**：
- 定义：`execution/ports.py` → `VisionPort`（`preflight`, `open_session`）+ `VisionSession`（`compare`, `detail`, `close`）。
- 适配器：`execution/adapters/vision.py` → `VisionAdapter`（注入 cancel_check/event_sink/progress_sink）→ `LocalQwenVLProvider` → `QwenVLSession`。
- 预检：`scripts/qwen_vl_runner.py --preflight`，检查 `config.json` + safetensors + CUDA。
- 知识层调用：`knowledge/visual_retrieval.py` 通过 `get_vlm_provider()` 获取 provider，Step 层在 `VisualEvidenceStep` 中管理会话生命周期。

**预检流程**（`create_visual_provider`）：
1. 检查 `local_vlm_enabled` 配置（`True`/`auto`/`False`）。
2. `preflight()` 验证 ImageT10 Python、runtime、runner、model 四路径存在。
3. 子进程执行 `--preflight`，返回 `{ok, cuda_available, device, ...}`。
4. `auto` 模式下预检失败 → `info` 级别日志（不报错），静默降级。
5. 非 `auto` 模式下预检失败 → `warning` 级别日志，明确告知。
6. 权重不完整 → 不下载模型，明确降级。
7. 无 CUDA → 不降级到 CPU，明确告知需要 GPU。

### 3.3 Cloud LLM — 云端大语言模型

| 维度 | 值 |
|------|------|
| 协议 | OpenAI 兼容 API（DashScope） |
| 客户端 | `FallbackChatClient`（`openai` SDK，`max_retries=0`） |
| 模型链 | `deepseek-v4-flash-0731` → `glm-5.2` → `kimi-k2.6` → `qwen3.7-plus` |
| 故障转移 | 依次重试，捕获 `APIConnectionError`/`APITimeoutError`/`APIStatusError`/`ValueError`/`JSONDecodeError` |
| 超时 | 90 秒/请求 |
| 生成参数 | `temperature=0.1`，`response_format={"type":"json_object"}`，`enable_thinking=False` |
| max_tokens | 默认 5000；规划 3200；丰富档 6000 |
| 取消 | daemon 线程 + queue 包裹阻塞 SDK 调用，取消时 `client.close()` |
| 截断处理 | `finish_reason=="length"` → 抛 `CloudOutputTruncated`，**不重试下一模型**（避免浪费预算） |
| 预算控制 | `CloudRequestBudget`，单视频 `max_calls_per_video`（默认 5），全流程共享 |

**模块边界**：
- 定义：`execution/ports.py` → `CloudJsonPort`（`request_json`, `request_json_with_info`）。
- 适配器：`providers.py` → `OpenAICloudJsonAdapter`（持有 `FallbackChatClient` + `CloudRequestBudget`）。
- 安全：`api_key` 不进入 `repr`（`compare=False, repr=False`）；错误信息简化为 `HTTP {code}`/`timeout`/`connection error`，不泄露响应体。
- 构造门控：`bootstrap.py` 中**仅** `cloud_authorized=True` 时注册 cloud Port 工厂；未授权时不构造客户端、不创建 OpenAI 实例。

## 4. 模态融合机制

知影的核心创新在于**音频（转写文本）与图像（关键帧）的深度融合**，而非简单拼接。以下是模态融合的 7 个交汇点：

### 4.1 融合点 1：帧选择对齐（`frames.select`）

关键帧选择**依赖** `transcript.normalized`——不是纯视觉采样，而是将关键帧与转写内容的时间线对齐。这使得后续的视觉证据能够关联到正确的讲解上下文。

### 4.2 融合点 2：视觉需求生成（`knowledge.plan`）

课程规划阶段从转写文本中推断**视觉画像**（`VisualProfile`）：
- 统计图表/屏幕/幻灯片/指认等术语的出现频率。
- 输出 `chart_analysis`/`screen_demo`/`slide_dominant`/`mixed`/`speech_dominant` 分类。
- `auto` 模式下根据画像自动决定视觉教学级别。
- 为每个需要视觉的知识点生成**像素可回答的视觉问题**（`visual_questions`），问题锚定到转写时间段（`anchor_spans`）。

### 4.3 融合点 3：视觉任务构建（`visual.jobs`）

从 plan 的视觉问题 + 转写上下文构建比对任务。每个任务携带：
- `question`：像素可回答的问题文本 + `success_criteria`（必须能从画面像素验证）。
- `candidates`：从关键帧召回的候选帧（每帧带时间戳、内容分、场景信息）。
- `contract`：视觉合同（角色、序列模式、成功标准、期望实体）。

### 4.4 融合点 4：VLM 像素核验（`visual.evidence`）

这是**模态融合的核心环节**——VLM 不是"看图说话"，而是**回答从音频内容衍生出的像素可验证问题**：

```
音频转写 → "这里讲到了 K 线的顶分型结构"
    ↓ 推断视觉需求
视觉问题 → "画面中是否可见标注了顶分型的 K 线图？"
    ↓ 召回候选帧（时间对齐 + 内容分 + 场景聚类）
VLM 比对 → 从候选帧中选择满足所有 success_criteria 的帧
    ↓ 细节复核
视觉证据 → {selected_frame, visible_evidence, criteria_met, criteria_missing}
```

**召回策略**（`recall_candidates_for_question`）：
1. 按场景聚类分组候选帧。
2. 每场景按 `content_score×0.8 + time_prior×0.2` 评分（时间作为弱先验，权重仅 20%）。
3. 可选 OCR 重排：对召回帧运行 OCR，按语义召回分数（OCR 命中率 × 内容分 × 场景类型 × 时间先验）重排。
4. 每问题最多 `max_candidates_per_question`（默认 6）个候选。

**VLM 核验流程**：
1. `compare_candidates`：VLM 从候选帧中选择满足所有 `success_criteria` 的帧，输出决策（select A/B/C/D/no_match）+ 可见证据 + 满足/未满足标准。
2. 交叉验证：将 VLM 报告的标准与合同文本通过 SequenceMatcher（≥0.78）匹配，确保 VLM 确实在核验正确的问题。
3. `extract_selected`（可选 detail pass）：对选中帧提取更详细的可见信息。

**仲裁**（`arbitrate_visual_evidence`）：
- 每场景最多 1 个主证据（DFS 去重，防止同一画面被多个知识点重复引用）。
- 输掉的证据折扣化（保留但不作为主证据）。
- 强制每单元 `max_count` 预算。

### 4.5 融合点 5：CourseIR 整合（`knowledge.course_ir`）

CourseIR 将**音频 claims** 和**视觉证据**整合为统一的知识表示：
- 每个知识单元的 claims 标记 `origin`：`audio_backed`（来自转写）、`visual_backed`（来自 VLM 证据）、`model_aid`（模型辅助生成）。
- 视觉证据仅取 `decision=="select"` 的结果，绑定到对应知识单元。
- `evidence_refs` 将知识单元同时关联到转写段（`segment_ids`）和关键帧（`frame_ids`）。

### 4.6 融合点 6：知识单元组装（`knowledge.units`）

整理后的 `KnowledgeUnit` 的 `content_blocks` 中同时包含：
- 文本块：paragraph / rule_list / steps / example / pitfall（来自音频 claims）。
- 视觉块：`visual_group`（含图片路径 + 看图重点 + 来源绑定）。
- 辅助块：understanding_tip / source_links。

**云端整理**时，LLM 收到的是紧凑的 CourseIR 投影（含 claims 文本 + 视觉事实），输出的是重组后的 content_blocks——视觉和文本在 LLM 层面被统一编排。

### 4.7 融合点 7：文档溯源（`document.assemble` + `render.bundle`）

最终文档中每个知识点的 `source_refs` 同时保存：
- `segment_ids`：对应的转写段 ID → 可追溯到原始音频时间戳。
- `frame_ids`：对应的视觉证据帧 ID → 可追溯到原始视频画面。
- `video-study://play/<video_id>?t=<seconds>`：点击即跳转到原视频对应时间点。

### 4.8 模态融合全景图

```
    音频路径                              图像路径
    ────────                              ────────
MP4 → audio.flac                    MP4 → candidates.jpg (600帧)
    ↓ ASR                                  ↓ 场景聚类 + 熵选择
transcript.raw                        frames.selected (≤8帧)
    ↓ 规范化                                ↓
transcript.normalized ──────┬─────── frames.selected
    ↓                       │               ↓
knowledge.plan ←─ 视觉画像推断     frames.semantics (语义标注)
    ↓                       │               ↓
visual.jobs ←── 视觉问题 + 时间锚        │
    ↓                       │               ↓
visual.evidence ←── VLM 像素核验 ────────┘
    ↓                       │
knowledge.course_ir ←─ claims + 证据融合
    ↓                       │
knowledge.units ←── content_blocks (文本 + 视觉块)
    ↓                       │
document.v2 ←── source_refs (segment + frame + 时间戳)
    ↓
Markdown / Word / PDF ←── video-study:// 可点击回看
```

## 5. 失败降级全路径

降级是知影的核心可靠性机制——**任何模型/云端失败都不应阻断流水线**，而是降级到更保守但可用的模式。

### 5.1 ASR 降级

```
引擎选择 (config.asr.engine)
  │
  ├─ faster-whisper
  │   ├─ device=auto → 尝试 CUDA
  │   │   ├─ 成功 → 正常转写
  │   │   └─ 失败（非取消）→ 降级到 CPU，记录 fallbacks=[{code:"asr_cuda_fallback"}]
  │   └─ device=cpu → 直接 CPU
  │
  ├─ qwen3-asr-0.6b
  │   └─ 子进程执行，失败即失败（无引擎内降级）
  │
  └─ 引擎链回退（transcript.decode Step）
      └─ 主引擎失败 → 尝试备用引擎，记录 fallbacks
```

**关键设计**：
- faster-whisper 的 CUDA 降级是**自动的**——任何非取消异常都触发 CPU 重试，用户无感知。
- 引擎间降级在 `TranscriptDecodeStep` 中实现，主引擎失败后尝试备用引擎。
- 降级信息记录在产物的 `fallbacks` 字段中，用于审计。

### 5.2 VLM 降级

```
local_vlm_enabled 配置
  │
  ├─ auto（默认）
  │   ├─ 预检通过 → 启用 VLM
  │   └─ 预检失败（权重缺失/无CUDA）→ 静默降级，info 级日志
  │       └─ visual.evidence 使用 _fallback_select（OCR-only 匹配）
  │
  ├─ true
  │   ├─ 预检通过 → 启用 VLM
  │   └─ 预检失败 → warning 级日志，明确告知用户
  │       └─ visual.evidence 使用 _fallback_select（OCR-only 匹配）
  │
  └─ false → 不启用 VLM
      └─ visual.evidence 使用 _fallback_select（OCR-only 匹配）
```

**VLM 运行时降级**：
- **OOM**：`VisualProviderOOMError` → 重试 2 帧候选（减少显存压力）。
- **会话失败**：`VisualProviderSessionError` → 重启会话一次（`restart_count`），再失败则 `close(force=True)` 并触发批次熔断。
- **批次熔断**：`_VLM_BATCH_FAILURE_SOURCES` 触发后，剩余任务全部走 `_fallback_select`。
- **Step 级降级**：`VisualEvidenceStep` 在任何异常时重试 `build_visual_evidence(provider=None)`，返回 `DEGRADED` + `degraded_reason`。

### 5.3 云端知识降级

```
cloud_authorized?
  │
  ├─ false → 全部使用离线模式
  │
  └─ true
      │
      ├─ knowledge.plan
      │   ├─ cloud 调用成功 → capability="cloud"
      │   └─ cloud 调用失败 → 回退 plan_offline → DEGRADED + "cloud_plan_offline_fallback"
      │
      ├─ knowledge.units
      │   ├─ cloud 调用成功 → capability="cloud"
      │   └─ cloud 调用失败 → 回退 organize_offline → DEGRADED + "course_ir_offline_fallback"
      │
      └─ document.assemble
          └─ 合并 cloud_info（含降级原因和 token 统计）
```

**关键设计**：
- 降级产出**仍然是有效的 Artifact**——runner 会 commit 和 cache DEGRADED 产出。
- 下次运行时若仍 `cloud_authorized=True`，cache 检测到 `produced_capability="offline"` vs `requested_capability="cloud"` → `CAPABILITY_INSUFFICIENT`，自动重跑。
- 降级原因记录在 `degraded_reason` 字段中，最终体现在文档的运行时元数据里。

### 5.4 云端预算耗尽

```
CloudRequestBudget.claim()
  │
  ├─ requests_used < max_requests → 正常调用
  │
  └─ requests_used >= max_requests → CloudBudgetExceeded
      └─ Step 捕获 → 降级到离线模式
      └─ 已有产物保留，不回退
```

**预算保护机制**：
- 预算是**全流程共享**的——规划、整理、聚合共享同一个 `CloudRequestBudget` 实例。
- 每次 `request_json_with_info` 前先 `budget.claim()`，超限即抛异常。
- 截断（`CloudOutputTruncated`）**不重试下一模型**——避免浪费预算在可能再次截断的请求上。
- 预算耗尽后，当前 Step 降级到离线，后续 Step 也只能用离线（除非用户增加预算重跑）。

### 5.5 渲染降级

```
PDF 渲染
  │
  ├─ 优先：Microsoft Word COM 导出
  │   ├─ 成功 → word-export.pdf
  │   └─ 失败（无 Word / COM 错误）→ reportlab 回退
  │
  └─ reportlab 回退
      ├─ 注册中文字体（msyh.ttc / simhei.ttf / simsun.ttc）
      ├─ 完整 content_blocks flowables 渲染
      └─ 含缩放图片 + 页脚
```

### 5.6 降级状态流转

| Step 状态 | 含义 | 产物 | 缓存 | 下次运行 |
|----------|------|------|------|---------|
| `SUCCEEDED` | 正常完成 | 有效 | 记录 | 缓存命中 |
| `DEGRADED` | 降级完成 | 有效（但能力较低） | 记录 | `CAPABILITY_INSUFFICIENT` 重跑 |
| `FAILED` | 失败 | 无 | 不记录 | `NO_RECORD` 重跑 |
| `CANCELLED` | 用户取消 | 无 | 不记录 | `NO_RECORD` 重跑 |
| `SKIPPED` | 依赖失败 | 无 | 不记录 | 按依赖链重跑 |

## 6. 缓存与恢复

### 6.1 缓存架构

每个视频的 Workspace 位于 `workspace/<video_id>/`，包含：

```
workspace/<video_id>/
├── manifest.json                    # source.probe 产物
├── audio/audio.flac                 # audio.extract 产物
├── transcript/raw.json              # transcript.decode 产物
├── transcript/transcript.json       # transcript.normalize 产物
├── transcript/transcript.srt
├── images/candidates.json           # frames.candidates 产物
├── images/keyframes.json            # frames.select 产物
├── images/candidates/               # 候选帧图片
├── images/keyframes/                # 精选关键帧图片
├── knowledge/lesson-plan.json       # knowledge.plan 产物
├── knowledge/visual-jobs.json       # visual.jobs 产物
├── knowledge/visual-evidence.json   # visual.evidence 产物
├── knowledge/frame-semantics.json   # frames.semantics 产物
├── knowledge/course-ir.json         # knowledge.course_ir 产物
├── knowledge/knowledge-units.json   # knowledge.units 产物
├── knowledge/selfcheck.json         # knowledge.selfcheck 产物
├── knowledge/document.json          # document.assemble 产物（Schema v2）
└── state/
    ├── pipeline-state.json           # 流水线状态快照
    ├── cache/<step>.json             # 每步缓存记录
    └── runs/<run_id>.jsonl           # 运行日志
```

### 6.2 缓存判定流程

`FileWorkspaceCache.decide()` 按优先级依次检查：

```
1. force_steps 包含此 Step? → FORCED（强制重跑）
2. 无缓存记录? → NO_RECORD
3. 缓存记录不可读? → PREVIOUS_RUN_INCOMPLETE
4. 实现版本变化? → STEP_VERSION_CHANGED
5. 合同版本变化? → CONTRACT_CHANGED
6. 指纹比较:
   ├─ upstream.* 组件变化 → UPSTREAM_CHANGED（上游产物变了）
   └─ 其他组件变化 → CONFIG_CHANGED（配置变了）
7. 能力不足? → CAPABILITY_INSUFFICIENT（请求 cloud 但只有 offline 产物）
8. 产物验证:
   ├─ 文件缺失 → OUTPUT_MISSING
   ├─ size/mtime 不变 → 跳过摘要，信任缓存
   └─ 摘要不匹配 → OUTPUT_CORRUPT
9. 以上都不满足 → CACHE_HIT（或 LEGACY_ADOPTED）
```

### 6.3 指纹机制

每个 Step 的 `fingerprint(ctx, inputs)` 方法返回 `FingerprintMaterial`，包含一组组件（key-value 对）：
- `upstream.<artifact_name>`：上游 Artifact 的 SHA-256 摘要。
- `config.<key>`：声明的配置项值。
- `source.fingerprint`：源视频内容指纹。

缓存记录存储 `cache_key = canonical_json_hash(components)` 和序列化的 `input_components`。下次运行时比较当前组件与存储组件的规范 JSON——**任何组件变化都精确分类为上游变化或配置变化**，从而确定重跑范围。

### 6.4 原子写入与回滚

`FileArtifactStore.commit()` 执行原子写入：
1. 在 staging 目录中验证所有输出文件存在且通过校验器。
2. 备份已有目标文件到 `.backup/`。
3. 原子移动 staging → workspace。
4. 计算 ArtifactRef（SHA-256 摘要 + size + mtime）。
5. 任何异常 → 回滚（恢复备份），抛出异常。

### 6.5 旧 Workspace 认领

`LegacyArtifactAdapter` + `LegacyAdoptingWorkspaceCache`：
- 遇到 `NO_RECORD` 时，尝试从磁盘认领已有产物。
- 单向只读认领——不修改旧产物，只写入缓存记录。
- Document v1 只允许 `v1_to_v2` 读取迁移；生产代码不写 v1。
- 历史文件不主动删除。

### 6.6 视觉任务缓存

VLM 比对结果通过 `FileTaskGroupCache` 缓存：
- 每个视觉任务的指纹基于问题 + 候选帧 + 合同的规范 JSON。
- 任务级缓存——即使关键帧集变化，未变化的任务仍可复用。
- 缓存先于 preflight/cold load——已缓存任务不需要加载模型。

## 7. 云端预算与截断分批

### 7.1 预算账本

`CloudRequestBudget` 是单视频全流程共享的预算控制器：

| 属性 | 默认值 | 来源 |
|------|--------|------|
| `max_requests` | 5 | `api.yaml → budget.max_calls_per_video` / `QWEN_MAX_CALLS_PER_VIDEO` |
| `max_input_chars` | 60000 | `api.yaml → budget.max_input_chars` / `QWEN_MAX_INPUT_CHARS` |
| `max_output_tokens` | 5000 | `api.yaml → budget.max_output_tokens` / `QWEN_MAX_OUTPUT_TOKENS` |
| `planning_max_output_tokens` | 3200 | `api.yaml → budget.planning_max_output_tokens` |
| `rich_max_output_tokens` | 6000 | `api.yaml → budget.rich_max_output_tokens` |

- `claim()` 在每次请求前递增 `requests_used`，超限抛 `CloudBudgetExceeded`。
- `usage` 累计 token 使用量（prompt_tokens + completion_tokens）。
- `attempts` 记录每次模型尝试的详细信息。

### 7.2 紧凑载荷

`build_cloud_payload(course_ir)` 将 CourseIR 投影为最小必要数据：

| 原始 | 投影 |
|------|------|
| Source blocks | `{id, t:[start,end]}` + raw_text（仅未被 claim 覆盖的） |
| Units | `{id, title, type, depth, source_ids}` |
| Claims | `{id, unit_id, kind, text, source_ids, origin}` |
| Visuals | `{visual_id, unit_id, role, facts, answer}`（仅 `decision=="select"`） |

**安全校验**（`_validate_payload_refs` + `_check_safe_value`）：
- 所有 `source_ids` 必须存在于 sources 中。
- 所有 `unit_id` 必须存在。
- 禁止任何本地路径、base64 数据、`*_path` 键、`data:image` 前缀。
- 禁止泄露 workspace 路径或视频路径。

### 7.3 截断分批

`plan_payload_batches` 将载荷拆分为多个批次以适应 token 上限：

- **输出 token 估算**（`_estimated_output_tokens`）：按 `detail_level` 加权——mention 90 / brief 200 / standard 380 / deep 620。
- **分批策略**：按单元分组，累加估计输出 token，超过 `max_output_tokens` 即开新批。
- **单单元溢出**：单个单元的估计输出超过 `max_output_tokens` → 报错（无法处理）。
- **跨批聚合**：document_title/overview/objectives/review/checklists/open_questions 跨批次合并。
- **响应校验**（`validate_cloud_response`）：拒绝响应中出现的任何不在载荷 ID 集合中的 ID（source_block_ids / plan_id / claim_ids / binding_id 等）。

### 7.4 多视频聚合

多视频聚合时，每个视频独立执行知识流水线，最终将多个 Document v2 聚合为一份综合文档：
- 每个知识点保留各自视频的来源回看链接。
- 按视频生成多个逻辑章节。
- 聚合阶段也共享同一个预算账本（如有云端授权）。
- 聚合降级：云端聚合失败时使用本地聚合（`local aggregate fallback`）。

## 8. 可溯源性保障

### 8.1 溯源链路

```
文档中的知识点
    ↓ content_blocks[].source_ids / claim_ids
KnowledgeUnit
    ↓ evidence_refs[].segment_ids + frame_ids
CourseIR claims + visual evidence
    ↓ source_ids → source_blocks
transcript.normalized segments（含 start/end 时间戳）
    ↓ timestamp_url(video_id, start)
video-study://play/<video_id>?t=<seconds>
    ↓ Windows 协议注册 → 本地播放器
ffplay -ss <seconds> 定位播放
```

### 8.2 溯源完整性保障

1. **Claim 指纹**：每个 claim 的 `source_ids` 关联到具体的转写段，SHA-256 指纹确保去重不丢源。
2. **视觉证据绑定**：`evidence_refs` 同时保存 `segment_ids` 和 `frame_ids`，文本和图像双向可溯。
3. **source_refs 保存**：Document v2 的 `source_refs` 是正文之外独立的溯源索引，不依赖 `content_blocks`。
4. **协议本地化**：`video-study://` 协议通过 `winreg` 注册到 Windows，点击链接调用本地播放器（优先 ffplay `-ss` 精确定位），不启动 Web 服务。
5. **时间戳钳制**：`clamp_segment_timestamps` 确保所有时间戳在 `[0, duration]` 范围内，避免越界。
6. **自检验证**：`knowledge.selfcheck` 的 `source_existence` 检查确保核心知识点不缺少 segment/frame 引用。

### 8.3 不可违反的边界

| 边界 | 保障机制 |
|------|---------|
| 视频不上传 | 云端只发送紧凑 CourseIR 投影，不含视频/截图/base64 |
| 密钥不泄露 | `ProcessingOptions` 拒绝 secret 字段；`CloudCredentials.api_key` 不进入 repr/比较；`.env` 被 .gitignore 忽略 |
| 云端默认关闭 | `bootstrap.py` 仅在 `cloud_authorized=True` 时注册 cloud Port 工厂 |
| 无 Web 服务 | 架构测试 `test_architecture_boundaries.py` 阻止 Web 服务/port/serve |
| 时间戳可追溯 | 全链路 segment → claim → content_block → source_refs → video-study:// |

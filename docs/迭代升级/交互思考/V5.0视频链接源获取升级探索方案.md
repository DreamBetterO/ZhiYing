# V5.0「视频链接源获取与下载」升级探索方案（已批准 · 作为 V5.0 执行依据）

> 状态：**已批准**（2026-08-19，用户确定版本为 V5.0 大版本并逐项拍板决策）。本文是 V5.0 的「探索/决策依据」文档；阶段、任务、验收门与**恢复点（checkpoint）**在 [V5.0 视频链接源获取升级执行计划](../V5.0视频链接源获取升级执行计划.md) 中定义。
> 基线：产品版本 `0.4.2`（V4.2）。**升级目标：V5.0（产品版本升至 `0.5.0`，大版本功能迭代）。**

## 0. 结论摘要（TL;DR）

1. **新增一个上游「源获取」阶段**，把「视频链接」先落成「本地缓存文件」，再原样送入现有 15 步流水线（`source.probe → … → render.bundle`）。**现有 15 步、CourseIR、Document v2、JSON→Markdown→Word→PDF、`video-study://` 回看、云端 opt-in 全部复用，几乎零改动。**
2. **优先「完整下载到本地缓存」**，而不是 B 站式「分段缓存/边下边处理」。原因是本项目存在两个代码级硬约束：`video-study://` 回看要求 `video.is_file()`（`localplay.py`），快速指纹要求文件大小 + 首尾 1MB（`utils.quick_fingerprint`）；且抽音频/抽帧本质需要整段可随机读的文件。分段缓存会破坏回看契约并重新引入 V4.2 刚修掉的「音频截断」类故障。
3. **下载引擎选 yt-dlp**（事实标准，支持 B 站等 1800+ 站点）：先 `--dump-json` 预检（判定是否失效/是否视频/是否需登录/是否 DRM/大小时长），再由用户确认后下载，支持进度、取消、断点续传、清晰度选择。
4. **UI 最小得体改动**：在工具栏加「添加链接」按钮 + 一个粘贴框；队列增加「来源」维度区分本地/链接；新增「下载中」进度阶段；预检结果先弹出确认框再下载。
5. **B 站**：普通 UGC 视频（无登录）可稳定获取，但 1080P 及以上通常需登录 Cookie（SESSDATA）；版权番剧/大会员专享/地区限制/DRM 无法绕过，必须「检测 + 友好提示」而非硬解。
6. B 站细节（§8）、测试资源（§9）、GitHub 同类项目参考（§10）均已由外部调研回填。
7. **七项设计决策已由用户逐项拍板（§12，2026-08-19）**：首启合规提示/不内置名单；首版不做登录态（B 站默认 480P）；清晰度自动降级链（1080P→720P→480P→360P）；清除缓存保留下载文件；yt-dlp 独立 exe 放 tools/；仅音频模式不进首版；已就绪后手动开始+可选连跑。

## 1. 现状基线与关键约束（代码证据）

### 1.1 当前来源链路是「纯本地文件」

- `application/requests.py::ProcessingRequest.video: Path` —— 来源只能是本地路径。
- `execution/bootstrap.py::run_compatible_pipeline` 第 150-154 行：`source_path = Path(video).resolve()`，`if not source_path.is_file(): raise FileNotFoundError`，然后用 `quick_fingerprint(source_path)` 生成 `video_id = safe_name(stem,48) + "-" + fingerprint`。
- `source.probe`（`steps/coarse.py`）对 `context.source.path` 跑 `ffprobe`；`audio.extract`/`frames.candidates` 对同一路径跑 `ffmpeg`。
- 全链路没有任何 URL/HTTP 下载能力（`grep` 仅命中 `urllib.parse` 的 URL 编码用途与云端 `openai` SDK）。

### 1.2 硬约束（决定「下载 vs 流式」）

| 约束 | 位置 | 影响 |
|---|---|---|
| `video-study://` 回看要求本地文件 | `localplay.py::launch_local_player`（`if not video.is_file(): raise`）+ `play_protocol_url` 通过 `manifest["source_path"]` 定位 | 回看必须指向本地文件，不能指向远端 URL |
| 快速指纹依赖文件大小 + 首尾 1MB | `utils.py::quick_fingerprint` | 流式源无法稳定计算指纹/缓存 |
| 抽音频 `ffmpeg -i <local>`、抽帧随机 seek | `media.py::extract_audio` / `frames.py` | 需要可随机读的本地文件，网络流易截断（V4.2 刚修 `audio_extract_incomplete`） |
| 桌面优先，无 Web UI/端口/serve | `AGENTS.md` / V4.0 合同 | 下载必须作为客户端后台任务，不能起服务 |
| `subprocess` 仅限基础设施 adapter | `AGENTS.md` | yt-dlp/ffmpeg 调用要收在 infra adapter 内 |
| `video_id` 决定 workspace 与缓存 | `bootstrap.py` | 同一链接重复处理要命中同一 workspace，不重复下载 |

### 1.3 文档/归档约定

- 版本时间线 `迭代记录与问题.md` 只在用户批准后追加一条；本文属「交互思考」执行文档，不进时间线。
- 便携打包：`tools/`、`models/` 增量复用；新增 yt-dlp 属于工具类，需在 `-RefreshTools` 门内说明。

## 3. 目标形态（用户视角）

- 用户粘贴一条链接（B 站、YouTube、直链 mp4、HLS 等）→ 点「解析」→ 秒级看到「标题 / 时长 / 体积 / 清晰度 / 是否可下」→ 确认「下载」或「取消」。
- 用户粘贴的不一定是「视频下载直链」，**更常见的是页面链接、短链、甚至 B 站分享口令（`BV` 号文本）**——产品要像爬虫一样**先「查找」再「判定」**：识别站点 → 解析页面/接口 → 提取视频信息；解析不出或判定不可用时，给出明确、可操作的提示（见 §4.2）。
- 下载在后台进行（与现有处理线程同一套取消/进度/事件机制）；**下载完成（含完整性校验通过）后队列显示「已就绪」并提示用户**，由用户勾选后点击「本地整理/云端优化」进入既有 15 步流水线（可选「下载并立即整理」连跑），产出与本地视频完全一致的 Markdown/Word/PDF + `video-study://` 回看。
- 再次粘贴同一链接 → 命中已下载缓存 → 直接「已就绪」复用（不重复下载、不重复 ASR）。

## 4. 核心设计决策

### 4.1 完整下载 vs 分段缓存（结论：完整下载为主）

**推荐「完整下载到本地缓存」，作为唯一主路径。** 依据：

1. `video-study://` 回看 + `quick_fingerprint` + ffmpeg 随机读，三条代码级约束都要求「本地完整文件」。
2. V4.2 刚修复「长视频音频覆盖不足 → 截断」；网络流式读入会重新引入这类偶发截断，且更难定位。
3. 现有 15 步零改动复用，开发与回归成本最低。

**流量友好的补偿手段（在「完整下载」框架内做，而不是改架构）：**

- 下载前先 `--dump-json` 预检，把体积/时长暴露给用户再确认。
- 清晰度选择（`-f` 格式选择），默认「适中」，用户可选标清省流量。
- 断点续传 `--continue`，失败重试不从头。
- 按 `video_id` 缓存，同链接不重复下载。
- **可选第二阶段（流量最优）**：「音频立即下 + 视频按需补下」两档规格（GitHub 同类项目启发，见 §10.2）：`-f ba` 先只下音频驱动 ASR（秒级出转写、体积小），`-f bv*+ba` 后台补下视频供抽帧与回看。需给 `transcript.decode` 增加「直接消费已下载音频」分支，不进入首版。

**不推荐分段缓存为主**的原因：分段缓存是为了「边下边播」，本产品要的是「一次性分析完整视频」，抽帧需要跨全片随机 seek、ASR 需要完整音频，分段省不了多少流量，却会破坏回看契约。

### 4.2 链接「查找」与「判定」（爬虫式预检，必须做）

**4.2.1 用户输入的形态远比「下载直链」广**——先做输入清洗与形态识别：

| 输入形态 | 示例 | 解析入口 |
|---|---|---|
| 视频文件直链 | `https://…/video.mp4` / `.webm` / `.mov` | 按扩展名识别 → 直接探测（HEAD/Range） |
| HLS/DASH 流 | `https://…/index.m3u8` | 按扩展名识别 → m3u8 拉流探测 |
| 视频站页面 URL | `bilibili.com/video/BV…`、`youtube.com/watch?v=…` | yt-dlp extractor（内置爬虫：请求页面/接口 → 提取元数据） |
| 短链 | `b23.tv/xxxx`、`youtu.be/xxx` | 302 跟随还原 → 再走页面解析 |
| **B 站分享口令 / 裸 ID** | 文本中的 `BV1xx…`、`av123456` | 正则提取 BV/av 号 → 直接查 `view` 接口 |
| 其他网页 | 新闻页、UP 主页、首页 | 无视频提取器命中 → 判「非视频链接」 |

**4.2.2 判定流程（对应 `SourcePort.preflight`）**：输入清洗（去空白/去前后缀文案/正则提取 URL 或 BV/av）→ URL 规范化（补 `https://`、展开短链、去跟踪参数）→ **站点识别**（yt-dlp `extractor` 匹配，本质即「爬虫式查找」）→ 元数据提取（`extract_info(download=False)`）→ **有效性判定**（下表）→ 结果卡片给用户确认。

**4.2.3 预检结果分类与提示文案（无效必须向用户明确提示，且可操作）：**

| 预检结果 | 判定依据（`--dump-json` 字段/异常） | 提示文案（示例） |
|---|---|---|
| 有效视频 | `title`/`duration`/`formats` 正常，`is_live=False`，`age_limit` 可满足 | 展示标题/时长/体积/清晰度 → 确认下载 |
| 失效/404 | extractor 抛 `Unsupported URL` / HTTP 404 | 「链接失效或视频已下架，请检查链接是否正确」 |
| 不是视频页 | 无 extractor 命中，或页面无媒体 | 「未识别到视频内容，请粘贴视频页面链接或 BV 号」 |
| 需登录 | `age_limit`/格式缺 1080P、extractor 提示登录 | 「该视频需要登录后才能获取更高清，是否导入浏览器 Cookie？」 |
| 地区限制/版权 | extractor 抛 region/georestriction | 「该内容受地区/版权限制，当前网络无法访问」 |
| DRM/付费 | 仅返回 DRM 流、extractor 抛 `Unsupported`/`DRM` | 「该内容含 DRM/付费保护，无法下载」 |
| 直播 | `is_live=True` | 「暂不支持直播内容」 |
| 体积超限 | `filesize_approx` > 阈值 | 「预估体积过大（X GB），可改选标清或取消」 |
| 网络不可达 | 连接/超时异常 | 「无法连接视频站点，请检查网络后重试」 |

> 预检阶段即拦截绝大多数失败（失效/非视频/需登录/大会员/地区/DRM），不会污染下游 ffmpeg 分析管线，也不浪费用户流量。

### 4.3 技术选型：yt-dlp

- **事实标准**：数千站点覆盖、周更活跃；B 站 Referer/UA/短链/分P/合集自动处理；支持库/CLI/独立 exe 三形态。替代方案 you-get（维护慢、B 站清晰度受限）、lux（Go 单文件、站点覆盖小）、gallery-dl（偏图站）、纯 ffmpeg 读 m3u8（需自己实现 API 解析/防盗链/DASH 合并，易碎）均不如 yt-dlp。
- **依赖 ffmpeg 合并**：B 站 720P+ 是 DASH m4s 分离流、m3u8 也要合并，yt-dlp 依赖 ffmpeg/ffprobe——**本项目已随包 ffmpeg/ffprobe**，零新增成本。
- **两种集成形态**（待实施二选一，均落在 infra adapter，绝不进业务/Step）：
  - A. **pip 包嵌入主运行时**（`import yt_dlp`，依赖含 `requests/certifi/mutagen/pycryptodome/websockets`）：`progress_hooks` 拿到 `status/downloaded_bytes/total_bytes(_estimate)/speed/eta/filename`，取消=hook 内抛异常，`extract_info(download=False)` 预检 + `try/except YoutubeDLError` 类型化分类；最顺，但需「依赖重装授权」+ PyInstaller 打包体积增大（要求 Python 3.10+，本项目主运行时满足）。
  - B. **独立 `yt-dlp.exe` 放 `tools/yt-dlp/`**，用 `subprocess`（复用 `LocalProcessAdapter`/`run_cancellable`）：无需 Python 依赖、可单独升级 exe（B 站反爬变动频繁时最友好）、便携增量友好；代价是进度/取消要靠 `--progress-template` + 解析输出，略繁琐。
- **建议**：**已按 D5 决策选 B（独立 exe 放 `tools/yt-dlp/`，用户已放置）**；进度/取消用 `--progress-template` + 解析输出。A（pip 嵌入）仅在需要更顺进度钩子时作为备选。
- **下载参数基线**（无论哪种形态，**D3 决策：默认最高 ≤1080P、获取失败依次降级**）：`-f "bv*[height<=1080]+ba/b"`、`--merge-output-format mp4`、`--continue`（默认开）、`--retries 10 --fragment-retries 10 --socket-timeout 30`、可选 `--limit-rate`、`--max-filesize`。
- **进度 UI 要点**：下载阶段与 ffmpeg 合并阶段是**两段进度**，进度条需分别处理（`status` 由 `downloading` → 合并/`finished`）；DASH 流的 `total_bytes` 常是 estimate，展示时用「已下 / 估算总量」口径，避免进度条回跳。

### 4.4 需要用户决策的合规点

- 下载他人视频存在版权/授权风险，且本产品本地整理已有「来源追溯」价值；**已按 D1 决策：UI 首次使用链接功能时提示「仅下载你有权访问的内容」；不内置站点黑/白名单（保留可配置 `deny_sites` 字段）**。

## 5. 架构升级方案

### 5.1 新增「源获取」阶段（在 `source.probe` 之前）

新增一个独立能力 `SourcePort` + 一个上游步骤 `source.acquire`（或一个「预流水线」服务），职责：

1. 规范化 URL（展开 b23.tv 短链、去跟踪参数）。
2. `--dump-json` 预检，产出 `SourceCandidate`（title、id、duration、size、formats、is_live、DRM、extractor）。
3. 生成稳定 `video_id`（优先 `id`，如 B 站 BV 号 / YouTube id；通用直链用 URL 规范化后哈希）。
4. 下载到 `workspace/<video_id>/source/<safe_title>.<ext>`（与 workspace 同生命周期，天然被 `WorkspaceCatalog` 管理）。
5. **下载完整性校验**：下载完成后对本地文件 `ffprobe`，`duration` 与预检 `duration` 偏差超阈值（如 >2% 或 >3s）即判「下载截断/不完整」并报 `DOWNLOAD_INCOMPLETE`，阻止进入下游（呼应 V4.2 `audio_extract_incomplete` 质量门，避免把坏源送进 ASR/抽帧）。
6. 返回本地 `Path` → 交给现有 `run_compatible_pipeline`。

**两种落地方式（实施时择一）：**

- **方式一（最小侵入，推荐）**：`run_compatible_pipeline` 之外新增 `run_compatible_pipeline_from_url(config, url, ...)`，内部「下载 → 得到本地 Path + 预生成 video_id/title → 复用 `run_compatible_pipeline`」。不触碰 15 步 DAG 与 `StepRegistry`，最稳。
- **方式二（内核化）**：把 `source.acquire` 注册为第 0 步，纳入 `StepRegistry`/`WorkspaceCache`（新 Artifact `source.download` + `SOURCE_ACQUIRE` 错误前缀 + 缓存命中逻辑）。更统一，但要改 `pipeline-steps.yaml`/`module-boundaries.yaml` 合同与合同测试，工作量大。

> 建议：首版走**方式一**（快速、低风险、可验证），待稳定后再评估是否内化成方式二。

### 5.2 DTO / 来源身份扩展（小改）

- `ProcessingRequest`：新增可选 `url: str | None = None`（与 `video: Path` 互斥），或新增 `SourceRef = Path | Url` 联合。
- `VideoSource`：新增可选 `display_title: str = ""`、`source_url: str = ""`（只读元信息，不进指纹秘密）。为避免改动 `source.probe`（它用 `path.stem` 当标题），**让下载文件名 = `safe_name(title)`**，则 `path.stem` 天然等于真实标题，零改动。
- `ProcessingResult` / `QueueItem`：新增 `source_kind`（`local` / `url`）与 `source_url` 用于 UI 展示与溯源。
- `WorkspaceCatalog`（`execution/artifacts.py`）：`find_by_source(source: Path)` 只按 `manifest["source_path"]` 匹配本地路径；链接源在「未下载前」没有本地路径。需新增 `find_by_url(url)`（或让 `source.manifest` 携带 `source_url` 并扩展匹配），使「重复粘贴同一链接」在下载前即可命中既有 workspace、不重复下载/重复 ASR。`delete_video` 对已下载链接源可按其本地缓存路径继续生效。

### 5.5 配置新增（`config.yaml` 与 api.yaml 之外的主配置）

```yaml
source:
  enabled: true
  download_dir: workspace            # 与 workspace 同根，便于 catalog 清理
  timeout_seconds: 30                # 预检超时
  max_bytes: 2147483648              # 单视频体积上限（2 GiB）
  format: "bv*[height<=1080]+ba/b"   # 默认最高≤1080P，获取失败依次降级（D3 决策）
  user_agent: ""                     # 留空用 yt-dlp 默认；注意部分站点（如 W3C）对浏览器 UA 反爬
  cookies_file: ""                   # 可选（D2 决策：首版无导入 UI，高级用户手动放置 Netscape cookies.txt）
  allow_sites: []                    # 可选白名单；空=不限制（D1 决策：不内置名单）
  deny_sites: []                     # 可选黑名单（D1 决策：字段保留，默认空）
```

### 5.6 错误码族（写入 problem-index.yaml）

`URL_INVALID` / `SOURCE_UNSUPPORTED_SITE` / `SOURCE_UNAVAILABLE`（失效/404）/ `SOURCE_NOT_VIDEO` / `SOURCE_LOGIN_REQUIRED` / `SOURCE_REGION_LOCKED` / `SOURCE_DRM` / `SOURCE_LIVE_UNSUPPORTED` / `DOWNLOAD_TIMEOUT` / `DOWNLOAD_TOO_LARGE` / `DOWNLOAD_INCOMPLETE`（时长一致性校验失败）/ `DOWNLOAD_FAILED`。每个映射到 owner（source adapter）、Artifact、测试与安全重跑范围。

## 6. UI 修改方案（得体、最小）

现有 UI：工具栏「＋ 添加视频」（文件对话框）、队列列 `顺序/选择/视频文件/状态/当前步骤/进度/已用/Token`、处理偏好、动作按钮（本地整理/云端优化/本地聚合/云端聚合）。

建议改动：

1. **工具栏新增「＋ 添加链接」按钮**（在「添加视频」旁），点击弹出一个小对话框：一个多行输入框 + 「解析」按钮 + 结果预览区（标题/时长/体积/清晰度/可下状态）+「下载」「取消」。
   - 解析是异步的，避免卡 UI（复用 `ProcessingHandle`/事件机制，但更轻量）。
   - 下载完成后**只进入「已就绪」状态（见第 4 条），不自动开始整理**，与本地视频「勾选后点本地整理/云端优化」的显式开始语义保持一致；对话框另提供可选「下载并立即整理」复选，勾选后才连跑流水线。
2. **队列列增加「来源」**（`本地`/`链接`，用小徽标），「视频文件」列对链接显示真实标题（来自下载文件名），悬停/详情显示原始 URL。
3. **状态/进度新增「下载中」阶段**：`状态=下载中`、`当前步骤=source.acquire`、进度条显示下载字节百分比与速度（yt-dlp `progress_hooks` 的 `downloaded_bytes/total_bytes/speed/eta`；注意「下载」与「ffmpeg 合并」是两段进度）。
4. **下载完成「已就绪」提示（本次新增需求）**：
   - **状态流转**：`下载中 → 已就绪（等待处理）→ 处理中 → 已完成`；队列状态列在下载成功后显示「已就绪」徽标（与本地视频的「等待中」同级、语义等价：可勾选 → 点「本地整理/云端优化」开始 15 步流水线）。
   - **提示形式（桌面得体、不打扰）**：① 状态列「已就绪」+ 当前步骤 `ready`；② 底部日志区追加「视频已下载完成，可勾选后点击『本地整理』开始处理」；③ 可选系统托盘/状态栏一次性提示（默认关闭，设置里可开）。**不用 messagebox 弹窗**（避免打断连续操作）。
   - **事件机制**：`SourcePort.acquire` 成功 + 下载完整性校验通过（§5.1 第 5 步）后，controller 发布 `UiEvent(kind="source_ready", …)`，View 统一刷新状态列与日志，不新增直接 Tk 调用。
   - **重复链接（缓存复用）**：再次粘贴同一链接且本地缓存有效时，直接进入「已就绪」并提示「已复用本地缓存，无需重新下载」。
   - **失败分支**：下载失败/完整性校验失败 → 状态「失败」+ §4.2 文案提示，**不进入「已就绪」**；重试不覆盖上一份有效产物。
5. **空面板文案**：从「点击添加视频…」改为「点击添加视频或添加链接」。
6. **打开原视频**：对链接源，指向下载后的本地缓存文件（`os.startfile`/ffplay），保持桌面离线回看，不跳网页。
7. **清除所选缓存**：对「本地源」与「链接源」语义一致——**保留原视频（含链接源的下载文件）**，只清派生产物（Workspace 中间产物、Output、失效聚合结果），与 D4 决策一致；下载文件仅在「清理全部缓存」时移除。
8. **失败提示**：把 §4.2 的预检结论映射为中文、可操作提示（例：「该视频需登录才能获取 1080P，是否导入浏览器 Cookie？」）。

## 8. B 站可行性结论

> 依据：yt-dlp 官方 extractor 现状与社区实证（2024–2025），关键来源见文末 URL。

### 8.1 能解决什么（普通 UGC 视频）

- **BV/av 号、分P 多P、UP 主合集（playlist）、b23.tv 短链**均受支持；短链经 302 跟随还原为 BV。
- **Referer / User-Agent 由 yt-dlp 自动处理**，无需手动拼头（这是 B 站防盗链的关键，缺 Referer 会 403/412）。
- 720P 及以上多为 **DASH（video.m4s + audio.m4s 分离流）**，需用**随包 ffmpeg 合并**成 mp4——本项目已随包 ffmpeg，天然满足。
- **无登录清晰度**：2024 年起收紧，匿名通常最高 **480P**；API 传 `try_look=1` 可暴露 720/1080 但下载仍受限。→ 应把「实际拿到什么清晰度」当作运行结果而非假设。
- 一句话：**普通 UP 主公开视频，无登录即可稳定获取（约 480P），是可靠的测试与产品主通道。**

### 8.2 不能绕过（必须「检测 + 友好提示」，不硬解）

| 情形 | 典型 yt-dlp 报错/信号 | 产品处置 |
|---|---|---|
| 1080P 及以上需登录 | 匿名拿不到高码率 | 提示「登录后可获取更高清」，提供 Cookie 导入入口 |
| 1080P60 / 4K / HDR / 杜比 / 8K（对应 qn=116/120/125·126/127） | `"Format(s) 1080P 高码率 are missing; you have to become a premium member"` | 提示「大会员专享清晰度」 |
| 番剧/影视版权、地区限制（海外 IP） | `"No video formats found"`（yt-dlp 已加 geo-block 检测） | 提示「受地区/版权限制」 |
| 大会员专享/付费/课堂/充电专属 | `"become a premium member"` / 不支持类型 | 提示「需会员/付费」 |
| DRM（Widevine/PlayReady/ClearKey） | `formats` 为空或带 `_has_drm`，`"This video is DRM protected"` | 提示「含 DRM 保护，无法下载」；**yt-dlp 无解密能力，不做绕过** |
| 失效/已删视频 | `"HTTP Error 404"` | 提示「链接失效或视频已下架」 |
| 非视频页 | `"Unsupported URL"` | 提示「未识别到视频」 |

### 8.3 预检落地方式

- 用 yt-dlp `extract_info(url, download=False)`（等价 `-J`/`--dump-json`）拿 `id/title/duration/formats/filesize/filesize_approx/is_live/live_status/age_limit/availability`，`try/except YoutubeDLError` 按 §8.2 的报错信号分类映射到 `SOURCE_*` 错误码。
- 预检阶段即可拦截绝大多数失败（失效/非视频/需登录/大会员/地区/DRM），**不会污染下游 ffmpeg 分析管线**，也避免白下载。

### 8.4 结论

- **B 站是「尽力而为」通道，不是核心承诺**：普通 UGC 可用（≈480P），高清晰度/版权/会员/地区/DRM 通过预检友好拦截。产品应把「来源解析失败」当作正常业务分支，而非 bug。
- 已知坑：Cookie 注入偶发格式缺失/404（需完整 Netscape 格式 cookie + `-J` 预检）；B 站反爬动态变化 → **锁定 yt-dlp 版本 + 定期升级 + 维护 B 站回归用例**。

### 8.7 抖音（Douyin）冒烟实测（⚠️ 待补）

| 环节 | 实测结果 |
|---|---|
| 可达性 | 首页/视频页/用户页 HTTP 200 |
| 页面内容 | **JS 空壳**：无 cookie 时页面仅返回 `<script>var glb;…`，无任何视频数据（抖音网页端反爬常态） |
| extractor | yt-dlp 2026.07.04 **有 `Douyin` extractor**（另含 TikTok 系列） |
| 数据/下载 | **实测结论：暂不可用**——yt-dlp 未实现抖音 web API 的 `a_bogus` 签名，`aweme/detail/` 返回空；**不纳入 V5.0 首版，UI 明确提示「暂不支持抖音」** |

**补充实测（2026-08-19 第二轮，含登录态尝试）**：
- 用户提供的 `/user/self?modal_id=…` URL：yt-dlp 报 **`Unsupported URL`**（该形态不是视频页，需转成 `/video/<ID>` 或 `v.douyin.com` 短链）。
- 构造的 `https://www.douyin.com/video/7674856617862597934`：extractor 识别出视频 ID，但 `aweme/v1/web/aweme/detail/` 返回空 → 报 **`Fresh cookies (not necessarily logged in) are needed`**。
- **根因排查（读 yt-dlp 源码 tiktok.py:1475-1486）**：报错有误导性。真正原因是抖音 web API **需要 `a_bogus`/`X-Bogus` 签名**，而 yt-dlp 的 `DouyinIE` **未实现签名**（其测试用例均为 2021 年、签名风控前）。即使提供登录 cookie，签名缺失仍会失败。
- 匿名 cookie 获取验证：`__ac_nonce`（访问首页）+ `ttwid`（`ttwid.bytedance.com/ttwid/union/register/`，`union register success`）均可匿名拿到；`s_v_web_id` 也可构造——**但都无法绕过签名门槛**。

**结论（重要）**：**抖音在 yt-dlp 当前版本下实测不可用**（web API 签名未实现）。若产品要支持抖音，需专门适配（a_bogus 签名逆向/注入 JS 执行、或换移动端接口），**不建议纳入 V5.0 首版**；先明确提示用户「暂不支持抖音」，避免承诺无法兑现。

### 10.2 关键经验（对你独有的取舍）

- 开源项目普遍三种取舍：**「只下音频」**（省流量但无法回看）、**「字幕优先/零媒体下载」**（最省流量但只做总结）、**「完整下载」**（可回看）。**知影要「回看原视频 + 抽帧图文」**，必须下视频本体，不能照抄前两种。
- **主流架构共识是「先完整下载到本地再处理」**（可续传、可缓存复用）；**「边下边转写」几乎没有成熟开源方案**（分段/对齐/重试复杂度高）——这印证了本方案 §4.1「完整下载」的选型。
- 两档规格启发（**后续增强，非首版**）：音频立即下驱动转写 + 视频按需/后台补下；首版仍以完整下载为主。
- **时间戳溯源**：whisperX 词级对齐（23k ⭐）重校准可提升回看精度——列为独立优化，不在本特性范围。
- **预检模式最值得抄**：yt-dlp `-J` / you-get `-i` / lux `-i` / YouTube oEmbed（无 Key）/ B 站 `view` API + `x/player/wbi/v2` 探测字幕。落地流程 = 粘贴 → 解析平台/ID → 元数据卡片 → 用户确认规格 → 下载 → 转写。

### 10.3 五条落地经验（借鉴 + 落地动作）

1. **抓取器抽象为三档接口**：把 yt-dlp 封装成 `metadata`（预检）/ `audio`（只拉音频）/ `full`（完整视频）三档的 `SourcePort`，产物进 `WorkspaceCache`，转写 Step 无感（对应 §5.1 方式一/方式二）。
2. **缓存分层**：音频立即下 + 视频按需下 + 可清理（与 §6.6、§12.4 的清理语义联动）。
3. **粘贴即预检 + 错误分类 + 可升级**：B 站 wbi 签名/接口版本做成可配置可升级，防风控（锁定 yt-dlp 版本 + 定期升级 + 回归）。
4. **下载后校验时长一致性**：下载完成后 ffprobe 本地文件，`duration` 与预检 `duration` 偏差过大即判「下载不完整/截断」，阻止进入下游（呼应 V4.2 的 `audio_extract_incomplete` 质量门）；同时记录 `format`/`offset` 元数据。
5. **隐私与合规**：本地转录保隐私；Cookie 不落盘或加密保存；遵守 ToS/版权（引以为戒：youtube-dl 曾因 DMCA 下架）；B 站接口限流退避防风控。

### 10.4 其它相关项目（按需参考）

- 转写引擎生态：openai/whisper（105k+）、ggml-org/whisper.cpp（52k，`examples/yt-wsp.sh` 即 yt-dlp 下音频→whisper.cpp 的最简范式）、SYSTRAN/faster-whisper（24k，知影已用）、m-bain/whisperX（23k）。

| 决策点 | 用户决策 | 落地影响 |

# 用户知识文档需求与工程优化讨论稿

更新时间：2026-08-06

## 1. 本次分析范围

- 用户提供的《新课.pdf》共 16 页，内容对应第 4、5、6 课“线段中枢”课程笔记。
- 对照了现有“推荐 / 丰富”实验产物、结构化知识 JSON、提示词、抽帧、聚合、渲染和桌面配置。
- 本轮只做需求提取和方案讨论，不改业务代码，不调用云端 API。

## 2. 从用户材料提取出的偏好与思考方式

用户材料数量有限，也包含个人理解，不能作为课程事实的标准答案或完整质量基准。它更适合用来观察用户如何选择、组织和呈现知识。以下结论描述的是用户偏好，不对材料中的具体知识结论作正确性背书。

### 2.1 内容目标

1. **核心知识必须展开，非核心内容可以极度压缩。**
   - “线段中枢、黑 K、肉与非肉、中枢取值、不重叠”等课程主线被详细拆解。
   - 大盘复盘等旁支只保留“讲解大盘 + 时间点”，没有平均分配篇幅。
   - 因此“丰富”不是全文均匀变长，而是按学习价值分配细节预算。

2. **规则型知识需要完整的判定结构。**
   - 定义：概念是什么。
   - 前置条件：判断前先确定什么。
   - 正反方向：上涨线段和下跌线段分别如何处理。
   - 操作步骤：从哪根 K 开始、向哪个方向寻找、何时停止。
   - 例外与边界：同价、跳空、延伸、连接关系、日线与 30F 的差异。
   - 正例、反例、易错例：为什么成立、为什么不成立。
   - 最终结论：可用于现场判断的短规则。

3. **不能只复述结论，要保留推导过程。**
   用户材料常用“定义 → 图示 → 编号解释 → 特殊情况 → 案例”的顺序。阅读者需要知道规则如何得到、如何用，而不只是看到一句总结。

4. **术语必须忠于课程内部体系。**
   这类课程存在“黑 K、起手三式、肉/非肉、中枢线确认 K、M5 反向”等自定义术语。整理系统应先建立本课程的术语表和定义关系，不能用通用金融知识自行补全或替换。

5. **必须保留不确定性和课程内矛盾。**
   如果 ASR、图示和口述无法确定，应标记待回看；如果不同段落表述冲突，应并列证据并提示复核，不能为了让文本流畅而擅自统一。

### 2.2 图文目标

1. 图不是装饰，而是规则证据。用户材料中的多数 K 线图承担“哪根 K、哪个区域、哪条轨、为何成立”的说明作用。
2. 一条复杂规则可能需要多张图：定义图、正例、反例、边界例，而不是一个知识点最多配一张代表帧。
3. 图片应紧邻其解释，并最好标出关联对象；仅写“同期画面”不足以支撑学习。
4. 需要区分课件页、行情图、讲师临时手绘、桌面/播放器画面。前三者可能是高价值证据，最后一类应过滤。
5. 图与文字都要保留精确来源时间，支持 `video-study://` 本地回看。

### 2.3 文档组织目标

推荐的知识单元不是固定的通用字段堆叠，而应按内容类型呈现：

| 知识类型 | 适合的表达结构 |
|---|---|
| 概念定义 | 定义、组成、与近似概念区别 |
| 判定规则 | 前置条件、决策步骤、成立/不成立、例外 |
| 取值算法 | 输入、方向分支、步骤、结果、特殊情况 |
| 案例讲解 | 背景、图中对象、逐步判断、结论、易错点 |
| 对比关系 | 对比表、共同点、差异、选择条件 |
| 课程旁支 | 简要记录、时间点、是否纳入复习主线 |

### 2.4 产品层面的隐含需求

- 默认自动判断课程领域和内容形态，但允许用户纠正。
- 用户更关心“这份资料能不能学懂”，而不是知识点数量、字符数或模型名称。
- “详细程度”之外还需要“整理目的”：复习提纲、系统学习、操作手册、会议纪要的结构完全不同。
- 自动整理必须可解释：哪些内容被详细展开、哪些被压缩、哪些因不确定而待回看。

## 3. 现有工程为什么仍然对不齐

### 3.1 不是单纯换一版提示词就能解决

现有丰富版提示词方向是对的，但上下游约束与目标冲突：

- 一个视频只参考约 8–10 个知识点，长课程天然会漏掉规则分支。
- 每个知识点的 `details / examples / conditions / pitfalls` 各最多 2 条，主动截断复杂规则。
- 整个视频一次性输入、一次性输出；第 4–6 课单视频压缩转写约 3.6–4.6 万字符，而输出上限 6000 Token，模型必须大幅取舍。
- 泛化 schema 只有“解释、细节、步骤、案例、条件、易错点”，无法明确表达正例/反例、方向分支、例外优先级、规则冲突和证据状态。
- 校验器主要检查 JSON 结构、字段长度和来源 ID 是否存在，不检查结论是否与原文相反。

### 3.2 已发现的具体质量信号

- 用户材料明确写“与 M5 同值不算黑 K”；现有丰富版写成“与五均线同价……是黑 K”。来源 ID 存在，但结论方向错误。
- 用户材料强调“反向一笔必须包含中枢线”，现有讲义没有把它稳定作为判定前提。
- 用户材料区分“起手三式形成过程进入前中枢”和“起手三式完成后再进入”的不同影响；现有讲义有概括过度的风险。
- 用户材料对大盘分析只留索引，现有丰富版却生成了较长的时效性操作建议，说明当前系统没有按用户学习目标分配篇幅。
- 现有产物中出现课程材料未稳定支持的扩展解释，说明模型会用领域常识填平转写空缺。

### 3.3 视觉证据链不足

- 当前关键帧主要按场景变化、图像熵和时间分桶选择，不知道“这张图是否解释了一个规则”。
- 丰富档最多约 12 张关键帧，且最小间隔可达 480 秒；对图表密集课程明显不足。
- 云端整理只接收压缩转写和来源块 ID，不接收图片、OCR、图中文字或画面类型。
- 最终关联方式是把图片分给时间上最近的知识点，并使用保守的“同期画面”图注；这能避免乱写图意，但不能形成用户材料那种逐图讲解。

### 3.4 领域适配不足

“先识别领域再整理”的方向正确，但仅识别“金融/医学/编程”仍不够。至少需要四层画像：

1. **领域**：金融技术分析、医学、软件操作等。
2. **课程形态**：规则教学、概念讲授、案例复盘、软件演示、会议讨论等。
3. **知识对象**：定义、判定规则、算法、案例、公式、代码、步骤、争议。
4. **用户目的**：快速复习、系统学习、操作执行、考试备考、存档检索。

领域画像只用于选择术语、结构、视觉策略和质量规则，不能默认引入外部事实。外部知识补充应是另一个显式授权的功能。

当前 `config.yaml` 里的 ASR hotwords 仍以医学术语为主，而本批视频属于金融技术分析课程；静态词表无法适应跨领域视频。

## 4. 建议的目标流水线

继续保留可恢复的 `JSON → Markdown → Word → PDF` 主链，但把“转写后一次调用生成全文”改为有证据账本的多阶段流水线：

```text
视频/音频
  → ASR + 时间戳
  → 画面候选 + 课件状态去重 + 本地 OCR
  → 内容画像（领域、课程形态、用户目的）
  → 知识内容鉴别（值得保留什么、属于什么知识类型）
  → 轻量课程地图（章节、主线/辅助/旁支）
  → 按知识类型专业化整理
  → 结构化知识单元与轻量自检
  → Markdown → Word → PDF
```

### 4.1 内容画像

- 使用文件名、前若干分钟转写、全局高频术语和本地 OCR 做初判。
- 输出领域、课程形态、建议模板、置信度和依据。
- 低置信度时使用通用模板，或在开始前让用户用一个下拉框纠正；不要阻塞本地 ASR。
- 支持课程级画像缓存，同一批连续视频复用术语表和结构偏好。

### 4.2 知识内容鉴别与选择

这是建议优先增加的核心能力。模型不应一上来就“写讲义”，而应先判断每段内容在课程中承担什么作用。

建议把判断拆成两个维度，避免把“重要程度”和“表达形态”混在一个标签里：

**内容角色：**

- 核心知识：后续内容依赖的定义、规则和方法。
- 支撑知识：用于解释核心知识的原因、比较、案例和图示。
- 边界知识：例外、限制、适用条件、反例和易错点。
- 课程导航：本节目标、章节过渡、后续预告。
- 时效旁支：大盘复盘、临时新闻、当时环境等。
- 口语噪声：寒暄、重复、互动口令、宣传和无信息表达。
- 待确认内容：ASR 不清、前后矛盾或依赖画面但缺少视觉证据。

**知识形态：**

- 概念/定义
- 判定规则
- 操作步骤/流程
- 原理/因果机制
- 对比/分类
- 案例/演示
- 例外/边界/反例
- 公式、数值、代码或图表解释
- 结论/复习要点

同一内容可以多标签。例如一个案例既是“支撑知识”，也可能同时包含“判定规则”和“反例”。分类应保存置信度，低置信度时使用通用整理方式，不应直接丢弃。

内容选择也不能只看单段文字。早期一句定义可能很短，却是后续一小时内容的前提。因此模型应先看到全局压缩目录或分段摘要，再判断主线、依赖关系和篇幅优先级。

建议在 JSON 中保存选择记录，但不必全部展示给用户：

```text
ContentDecision
  source_refs
  role_tags[]
  knowledge_types[]
  importance               # core / supporting / peripheral
  keep_mode                # expand / concise / index_only / omit
  confidence
  reason
```

这样既能让系统解释“为什么这个内容详细、那个内容只留时间点”，又能在后续调整偏好时复用 ASR 和画面缓存重新整理。

### 4.3 轻量课程地图

先生成“要覆盖什么”，再写正文。课程地图至少包含：

- 核心概念及其依赖关系。
- 讲者明确强调的重点。
- 规则、方向分支、例外、案例和未回答问题。
- 核心/辅助/旁支优先级。
- 每项对应的时间区间和候选画面。

这一步不需要成为复杂的人工评测标准，只需要充当一次生成过程中的内部提纲。它能避免模型在一个大请求里凭印象挑 8–10 个点，也能让“丰富”表现为核心内容更深，而不是所有内容更长。

### 4.4 按知识类型专业化整理

先分类、再专业化整理，通常会比一条通用“专业版提示词”更好。不同知识形态需要回答的问题不同：

| 知识类型 | 专业整理重点 |
|---|---|
| 概念/定义 | 上位概念、组成、定义边界、与近似概念区别 |
| 判定规则 | 前置条件、判断顺序、方向分支、成立/不成立、例外 |
| 操作流程 | 输入、步骤、停止条件、输出、失败处理 |
| 原理机制 | 前因、过程、结果、适用范围，避免补造因果 |
| 对比分类 | 对比维度、共同点、差异、选择条件 |
| 案例演示 | 背景、图中对象、逐步应用规则、结论、可迁移经验 |
| 边界反例 | 违反哪一条件、为何不成立、最容易误判之处 |
| 图表/公式 | 符号或对象、读图顺序、对应口述、不能从图中确认的部分 |

实现时不必为每种类型单独发起一次模型请求。更适合个人项目的做法是维护一组可组合的提示词模块：基础忠实性规则 + 领域术语提示 + 当前知识类型整理模板。一个语义章节可以在一次调用中输出多个不同类型的知识单元。

分类结果也不应成为不可更改的硬路由。如果整理过程中发现某段实际包含规则或反例，允许补充标签；分类置信度低时退回通用知识单元。这样可以降低“分错类型后越整理越错”的风险。

### 4.5 分块证据抽取

- 按语义章节切块，而不是整段一次提交；块间保留少量重叠。
- 每块只抽取原子事实和证据，不急着写优美讲义。
- 每条原子事实必须绑定 `segment_ids`，可选绑定 `frame_ids / OCR 区域`。
- 明确保存 `asserted / uncertain / conflicting / visual_only` 等证据状态。
- 云端调用次数和预计 Token 在用户确认时展示；仍保持云端 opt-in。

### 4.6 面向内容类型的知识 schema

建议把通用 `knowledge_point` 扩展为可演进的知识单元：

```text
KnowledgeUnit
  id, type, title, importance
  definition / conclusion
  prerequisites
  branches[]                 # 例如上涨 / 下跌
  procedure[]
  rules[]                    # 条件 → 结论
  exceptions[]
  positive_examples[]
  negative_examples[]
  pitfalls[]
  unresolved[]
  evidence_refs[]            # segment、frame、OCR
```

渲染器根据 `type` 选择定义卡片、决策表、步骤列表、案例块或对比表。旧 schema 可通过 adapter 继续读取，避免破坏已有缓存和产物。

### 4.7 图像策略

- 候选采样可以保持本地，但应增加“教学画面”评分：OCR 文本变化、图表区域、手写/标注变化、鼠标讲解停留等。
- 先做课件状态去重，再按知识单元选图；不要先硬性压到 12 张再关联知识点。
- 同一规则允许保留正例、反例和边界例多张图。
- 第一阶段可只把本地 OCR 和画面元数据发给语言模型，图片本身不上传。
- 若后续启用视觉模型，应单独提示“会上传候选截图并消耗额度”，默认关闭。
- 图注分两级：自动确认的具体说明；无法确认时继续使用“同期画面”的保守说明。

### 4.8 适合个人项目的轻量自检

不建立需要大量人工标准答案、评测集或独立模型调用的“质量门”。用户材料也不作为逐条事实答案。只保留几项低成本、能直接防止明显错误的生成期检查：

- 每个核心知识单元至少有一个来源时间段。
- 判定规则如果原文出现否定、同价、前后、上下、例外等方向词，整理结果必须保留对应表达。
- 标记为“详细展开”的规则，检查是否遗漏原文明确出现的条件、步骤或例外字段。
- 同一术语在本视频内出现明显相反说法时，不自动合并，标记待回看。
- 依赖画面的内容如果没有匹配图，只写“需结合原画面确认”，不推测图意。
- 生成后输出少量过程统计，例如核心项数量、仅索引旁支数量、待确认数量，供开发者快速抽查。

这些检查可以主要由确定性代码完成，必要时复用当前整理调用的结构化结果，不额外消耗大量模型额度。日常优化采用“小样本人工看一遍”的方式即可，不要求建设正式评测体系。

## 5. 产品交互建议

不建议把大量专业选项直接堆到桌面首页。可以保留当前“精简 / 推荐 / 丰富”，新增一个折叠的“整理偏好”：

- 整理用途：快速复习 / 系统学习 / 操作手册。
- 内容领域：自动识别，可手动纠正。
- 重点：核心理论 / 操作步骤 / 案例与图解。
- 视觉增强：本地图文对齐；可选云端视觉复核（明确额度和上传范围）。

处理前确认页应显示：识别到的领域和课程形态、计划详细展开的主线、预计云端调用次数/Token、是否会上传图片。

## 6. 工程结构建议

### 6.1 是否需要换框架

暂不建议重写或换成 Web / 本地服务。当前问题的主因是知识流水线、schema 和模块边界，不是 Tkinter 或 Python 本身。继续采用“原生桌面 + 模块化单体”更符合现有打包、离线处理和 `video-study://` 协议约束。

如果未来桌面交互复杂到需要画布标注、人工校订或多窗格编辑，再单独评估 PySide6；现在切换 UI 框架会扩大打包和回归成本，却不会直接改善讲义质量。

### 6.2 当前结构的主要问题

- `desktop.py` 约 1005 行，混合 UI、状态、配置保存、任务编排和缓存操作。
- `summarize.py` 约 590 行，混合离线摘要、云端 prompt、校验、schema 归一化、配图和缓存。
- prompt 嵌在 Python 字符串中，难以版本化、对比、按领域组合和用少量样例回归。
- `aggregate.py` 又实现一套相似 schema 与提示词，单视频和聚合容易逐渐不一致。
- 实验脚本直接依赖桌面内部函数，说明应用层边界不清。
- 源码、构建、发行包、Node 依赖、模型和用户产物都在根目录可见，开发视图噪声很大。

### 6.4 本地数据和构建产物

- `Resource/、workspace/、output/、models/` 继续视为本地数据，不参与源码重排。
- 中期可以引入统一 `data_root`，把开发态本地数据集中到 `var/` 或用户数据目录；迁移时必须兼容旧路径和已有缓存。
- `build/、pack/、node_modules/、tmp/` 属于构建/临时产物，保持忽略，并在开发文档中明确生成来源。
- 根目录只保留启动、配置、项目元数据和高层说明；Windows 打包细节收敛到 `packaging/windows/`。

## 7. 建议实施顺序

### 阶段 A：先固定偏好模型，不建立重型评测

1. 把《新课.pdf》提炼为“用户偏好配置”：核心知识展开、规则型呈现、图文结合、旁支压缩、保留时间索引。
2. 不把其中的具体知识结论写成系统标准答案，也不要求以后的视频与它逐条对齐。
3. 只保留几个可确定性检查的底线规则，并通过少量真实产物人工抽查调整。

### 阶段 B：先改知识中间层，再改 UI

1. 引入 `CourseProfile / ContentDecision / CourseMap / KnowledgeUnit / EvidenceRef`。
2. 先实现知识内容鉴别、保留策略和知识类型标签。
3. 拆出可组合的 prompt 模块和版本号，按知识类型专业化整理。
4. 实现分块证据抽取和轻量冲突提示。
5. 保留旧 JSON adapter，维持 Markdown → Word → PDF 和时间戳链接。

### 阶段 C：增强视觉但保持隐私默认

1. 本地 OCR、课件状态去重、教学画面评分。
2. 知识单元驱动选图和多图案例。
3. 视觉模型作为独立 opt-in 复核，不作为默认必需依赖。

### 阶段 D：模块迁移与桌面交互

1. 先拆 `summarize.py`，因为它直接决定内容质量。
2. 再拆 `desktop.py` 的状态、用例和视图。
3. 最后整理脚本、测试和 packaging；每一步保持旧入口和安装包可运行。

## 8. 当前建议结论

1. 用户的判断基本正确：需要根据领域进一步整理，但真正有效的适配单位应是“领域 + 课程形态 + 知识对象 + 用户目的”。
2. 下一轮不宜只继续加长“专业版提示词”；应优先解决一次性压缩、schema 过泛、视觉缺席和缺少基本事实自检的问题。
3. 现有 Python 原生桌面框架仍可承载目标功能，推荐渐进式模块化，不建议此时重写 UI 或引入 Web 服务。
4. 最值得先做的 MVP 是：从现有转写中先产生 `ContentDecision`，把内容分成“展开 / 简写 / 仅索引 / 忽略”，再按知识类型生成不同结构的 `KnowledgeUnit`；用户 PDF 只用于设置呈现偏好，不作为事实评测标准。
